# 1. PURPOSE

این سند الزامات طراحی، پیاده‌سازی، آزمون و ارزیابی دسترس‌پذیری رابط کاربری اکوسیستم Eco Nojin را تعریف می‌کند.

هدف، ایجاد تجربه‌ای قابل استفاده برای طیف متنوعی از کاربران، از جمله افراد دارای محدودیت‌های بینایی، شنوایی، حرکتی، شناختی و کاربران دارای محدودیت‌های موقت یا موقعیتی است.

دسترس‌پذیری نباید به‌عنوان یک قابلیت جانبی یا مرحله اصلاحی پس از تکمیل طراحی تلقی شود. این موضوع باید از مرحله معماری اطلاعات و طراحی اولیه تا توسعه، آزمون و انتشار در چرخه محصول حضور داشته باشد.

## 1.1. اهداف اصلی

1. دسترسی به محتوای اصلی بدون وابستگی به رنگ، تصویر یا صدا.
2. امکان استفاده از سامانه با صفحه‌کلید.
3. سازگاری با فناوری‌های کمکی.
4. خوانایی مناسب متن و داده‌های علمی.
5. پشتیبانی صحیح از RTL و LTR.
6. کاهش موانع شناختی و تعاملی.
7. پشتیبانی از دستگاه‌های مختلف و کاربران دارای محدودیت‌های فنی.
8. حفظ دسترس‌پذیری در نمودارها، نقشه‌ها و ابزارهای علمی.
9. ارائه پیام‌های خطا و وضعیت‌ها به شکل قابل درک.
10. ایجاد فرآیند قابل اندازه‌گیری برای ارزیابی انطباق.

## 1.2. اصل بنیادین

هیچ قابلیت، صفحه یا کامپوننتی صرفاً به دلیل داشتن ظاهر مناسب، زیبا یا واکنش‌گرا، دسترس‌پذیر محسوب نمی‌شود.

دسترس‌پذیری باید با آزمون واقعی و ثبت شواهد ارزیابی شود.

# 3. INCLUSIVE DESIGN PRINCIPLES

طراحی فراگیر باید بر اصول زیر استوار باشد:

## 3.1. Perceivable

اطلاعات و اجزای رابط باید به روش‌های مختلف قابل دریافت باشند.

## 3.2. Operable

کاربران باید بتوانند بدون وابستگی به روش ورودی خاص، با رابط تعامل کنند.

## 3.3. Understandable

محتوا، ساختار و رفتار سامانه باید قابل فهم و قابل پیش‌بینی باشند.

## 3.4. Robust

رابط باید با مرورگرها و فناوری‌های کمکی سازگار باشد.

## 3.5. Inclusive Beyond Disability

طراحی باید محدودیت‌های موقعیتی را نیز در نظر بگیرد:

- نور شدید محیط.
- نمایشگر کوچک.
- اینترنت ضعیف.
- دستگاه قدیمی.
- خستگی چشم.
- استفاده با یک دست.
- محدودیت سواد دیجیتال.
- محیط‌های پرصدا.
- استفاده در فضای باز.
- شرایطی که کاربر امکان پخش صدا ندارد.

# 4. ACCESSIBILITY ARCHITECTURE

دسترس‌پذیری باید در چهار سطح معماری پیاده‌سازی شود.

| Layer | Responsibility |
|---|---|
| Design | پیش‌بینی نیازهای دسترس‌پذیری در طراحی |
| Components | ایجاد رفتار استاندارد در کامپوننت‌ها |
| Features | حفظ دسترس‌پذیری در قابلیت‌های تخصصی |
| Validation | آزمون و تأیید شواهد انطباق |

## 4.1. Design Layer

الزامات:

- کنتراست مناسب.
- اندازه متن قابل خواندن.
- سلسله‌مراتب بصری روشن.
- عدم اتکای صرف به رنگ.
- فاصله مناسب عناصر تعاملی.
- پیش‌بینی حالت Focus.
- طراحی خطا و پیام‌های وضعیت.
- امکان بزرگ‌نمایی محتوا.

## 4.2. Component Layer

کامپوننت‌های مشترک باید رفتار دسترس‌پذیر را به‌صورت پیش‌فرض ارائه دهند.

نمونه:

- Button
- Input
- Select
- Checkbox
- Radio
- Switch
- Dialog
- Drawer
- Tabs
- Tooltip
- Accordion
- DataTable
- Pagination
- Notification
- Breadcrumb
- Navigation
- Search

## 4.3. Feature Layer

ویژگی‌های تخصصی باید با توجه به ماهیت خود ارزیابی شوند.

نمونه:

- نقشه‌های علمی.
- نمودارهای اقلیمی.
- مدل‌های شبیه‌سازی.
- تحلیل سنجش‌ازدور.
- ابزارهای مالی.
- فرآیند خرید.
- فرم‌های ثبت پروژه.
- داشبورد مدیریتی.

## 4.4. Validation Layer

هر قابلیت باید شواهد آزمون داشته باشد.

وجود Attributeهایی مانند `aria-label` یا `role` به‌تنهایی اثبات دسترس‌پذیری نیست.

# 5. SEMANTIC HTML STANDARDS

استفاده از HTML معنایی باید بر ساختارهای سفارشی و غیرضروری مقدم باشد.

## 5.1. Required Semantic Elements

| Purpose | Preferred Element |
|---|---|
| Main page header | header |
| Main navigation | nav |
| Main content | main |
| Independent section | section |
| Standalone content | article |
| Complementary content | aside |
| Footer | footer |
| Action | button |
| Navigation | a |
| Form input | input |
| Form label | label |
| Data table | table |

## 5.2. Document Structure

هر صفحه باید ساختار معنایی قابل تشخیص داشته باشد.

نمونه:

```html
<body>
  <header>
    <nav aria-label="ناوبری اصلی">
      ...
    </nav>
  </header>

  <main id="main-content">
    <h1>داشبورد علمی</h1>

    <section aria-labelledby="water-heading">
      <h2 id="water-heading">تحلیل منابع آب</h2>
      ...
    </section>
  </main>

  <footer>
    ...
  </footer>
</body>
```

## 5.3. Heading Hierarchy

قواعد:

- هر صفحه باید عنوان اصلی مشخص داشته باشد.
- ترتیب عنوان‌ها باید منطقی باشد.
- استفاده از Heading صرفاً برای بزرگ کردن متن ممنوع است.
- سطح عنوان نباید به دلیل ظاهر بصری انتخاب شود.
- عنوان‌های تکراری و مبهم باید از هم متمایز شوند.

## 5.4. Main Landmark

هر صفحه باید یک ناحیه اصلی محتوایی قابل تشخیص داشته باشد.

## 5.5. Skip Navigation

در صفحات دارای Navigation تکرارشونده باید امکان عبور مستقیم به محتوای اصلی فراهم باشد.

نمونه:

```html
<a class="skip-link" href="#main-content">
  رفتن به محتوای اصلی
</a>
```

این لینک باید هنگام دریافت Focus قابل مشاهده باشد.

# 6. KEYBOARD ACCESSIBILITY

تمام قابلیت‌های تعاملی باید با صفحه‌کلید قابل استفاده باشند.

## 6.1. Required Keyboard Support

| Key | Expected Behavior |
|---|---|
| Tab | انتقال به عنصر بعدی |
| Shift + Tab | انتقال به عنصر قبلی |
| Enter | فعال‌سازی لینک یا کنترل مربوط |
| Space | فعال‌سازی کنترل‌های مناسب |
| Escape | بستن Dialog یا منوی قابل بستن |
| Arrow Keys | پیمایش در الگوهای تعاملی مربوط |
| Home | رفتن به ابتدای فهرست یا ناحیه مربوط |
| End | رفتن به انتهای فهرست یا ناحیه مربوط |

رفتار کلیدها باید متناسب با الگوی تعاملی انتخاب شود و نباید برای تمام کامپوننت‌ها یکسان فرض شود.

## 6.2. Keyboard Traps

کاربر نباید در یک کامپوننت گرفتار شود.

استثناهای محدود مانند Dialog باید مسیر خروج روشن و استاندارد داشته باشند.

## 6.3. Focus Visibility

Focus باید:

- قابل مشاهده باشد.
- با پس‌زمینه کنتراست کافی داشته باشد.
- زیر عناصر دیگر پنهان نشود.
- با Scroll یا تغییر صفحه از دید خارج نشود.
- در حالت Keyboard Navigation حفظ شود.

## 6.4. Focus Appearance

برای طراحی نشانگر Focus:

- از Border یا Outline قابل مشاهده استفاده شود.
- از حذف `outline` بدون جایگزین مناسب خودداری شود.
- در پس‌زمینه‌های مختلف، قابلیت تشخیص حفظ شود.
- نشانگر Focus نباید صرفاً با تغییر رنگ ظریف مشخص شود.

## 6.5. Focus Not Obscured

عناصر دارای Focus نباید توسط موارد زیر پوشانده شوند:

- Header ثابت.
- Footer ثابت.
- Modal.
- Cookie Banner.
- Floating Action Button.
- نوارهای اعلان.
- پنل‌های شناور.

# 7. SCREEN READER COMPATIBILITY

رابط باید برای کاربران فناوری‌های کمکی قابل درک باشد.

## 7.1. Accessible Names

هر عنصر تعاملی باید نام دسترس‌پذیر معنادار داشته باشد.

نام باید عملکرد عنصر را مشخص کند.

نام‌های نامناسب:

- کلیک کنید.
- بیشتر.
- مشاهده.
- دکمه.

نمونه‌های بهتر:

- مشاهده جزئیات وضعیت آبخوان.
- دانلود گزارش تحلیل خاک.
- ثبت درخواست عضویت در بازارگاه.

## 7.2. Decorative Elements

عناصر صرفاً تزئینی نباید به‌عنوان محتوای غیرضروری به Screen Reader منتقل شوند.

نمونه:

```html
<img src="/assets/decoration.svg" alt="" />
```

## 7.3. Meaningful Images

تصاویر معنادار باید توضیح متنی مناسب داشته باشند.

متن جایگزین باید اطلاعات ضروری تصویر را منتقل کند، نه اینکه صرفاً نام فایل یا عبارت «تصویر» را تکرار کند.

## 7.4. Icon Buttons

دکمه‌های آیکونی باید نام دسترس‌پذیر مشخص داشته باشند.

نمونه:

```html
<button type="button" aria-label="بستن پنجره">
  <svg aria-hidden="true">
    ...
  </svg>
</button>
```

## 7.5. Live Regions

برای اعلام تغییرات مهم رابط می‌توان از Live Region استفاده کرد.

نمونه:

```html
<div aria-live="polite" aria-atomic="true">
  گزارش با موفقیت ذخیره شد.
</div>
```

استفاده از Live Region باید محدود و هدفمند باشد.

اعلام مداوم تغییرات غیرضروری باعث اختلال در تجربه کاربر می‌شود.

## 7.6. Status Messages

موارد زیر باید در صورت لزوم برای فناوری‌های کمکی قابل تشخیص باشند:

- ذخیره موفق.
- خطای ثبت.
- تکمیل بارگذاری.
- نتیجه جست‌وجو.
- تغییر وضعیت سفارش.
- پایان پردازش.
- قطع اتصال.
- بازیابی اتصال.

# 8. COLOR AND CONTRAST ACCESSIBILITY

رنگ نباید تنها ابزار انتقال معنا باشد.

## 8.1. Contrast Requirements

حداقل نسبت‌های کنتراست مطابق WCAG 2.2:

| Content | Minimum Contrast |
|---|---:|
| Normal Text | 4.5:1 |
| Large Text | 3:1 |
| UI Components | 3:1 |
| Meaningful Graphical Objects | 3:1 |

متن بزرگ مطابق تعریف WCAG:

- حداقل 18pt در وزن معمولی.
- حداقل 14pt در وزن Bold.

## 8.2. Non-Text Contrast

عناصر زیر باید کنتراست قابل تشخیص داشته باشند:

- Border ورودی‌ها.
- آیکون‌های کاربردی.
- کنترل‌های انتخاب.
- نشانگرهای Focus.
- اجزای ضروری نمودار.
- مرزهای عناصر تعاملی.

## 8.3. Color Independence

نمونه‌های نامناسب:

- نمایش خطا فقط با رنگ قرمز.
- نمایش موفقیت فقط با رنگ سبز.
- نمایش شدت خشکسالی فقط با تغییر رنگ.
- نمایش وضعیت سفارش صرفاً با رنگ Badge.

روش مناسب:

رنگ + متن + آیکون یا نشانه بصری مکمل.

## 8.4. Color Palette Validation

تمام رنگ‌های چهار مسیر هویت بصری باید از نظر کنتراست ارزیابی شوند.

این بررسی باید برای حالت‌های زیر انجام شود:

- Light Background.
- Colored Surface.
- Interactive State.
- Disabled State.
- Data Visualization.
- Focus State.
- Error State.
- Warning State.
- Success State.

هیچ رنگ پیشنهادی در اسناد هویت بصری به‌صورت خودکار دسترس‌پذیر تلقی نمی‌شود.

# 9. TYPOGRAPHY AND READABILITY

تایپوگرافی باید برای خوانایی در زبان‌های فارسی و انگلیسی طراحی شود.

## 9.1. Typography Requirements

- اندازه متن اصلی باید برای خواندن طولانی مناسب باشد.
- فاصله خطوط باید از فشردگی متن جلوگیری کند.
- وزن فونت نباید خوانایی را کاهش دهد.
- تفاوت وزن‌ها باید قابل تشخیص باشد.
- استفاده بیش از حد از حروف بزرگ لاتین محدود شود.
- متن‌های طولانی باید ساختار پاراگرافی مناسب داشته باشند.

## 9.2. Text Resize

محتوا باید با بزرگ‌نمایی متن تا 200 درصد قابل استفاده باقی بماند.

## 9.3. Text Spacing

رابط باید تغییرات فاصله‌گذاری متن را بدون از دست رفتن محتوا یا عملکرد تحمل کند.

معیارهای آزمون:

- Line Height حداقل 1.5 برابر اندازه فونت.
- فاصله پس از پاراگراف حداقل 2 برابر اندازه فونت.
- Letter Spacing حداقل 0.12 برابر اندازه فونت.
- Word Spacing حداقل 0.16 برابر اندازه فونت.

این مقادیر باید در آزمون Text Spacing به کار روند؛ الزام به استفاده دائمی از این مقادیر در تمام طراحی‌ها نیست.

## 9.4. Persian Typography

موارد زیر باید بررسی شوند:

- اتصال صحیح حروف فارسی.
- نیم‌فاصله.
- اعداد فارسی و لاتین.
- علائم نگارشی.
- ترکیب متن فارسی و انگلیسی.
- نمایش صحیح واحدهای علمی.
- شکست خطوط.
- نمایش اعداد اعشاری.
- سازگاری فونت با Screen Reader.

## 9.5. Long Scientific Text

محتوای علمی طولانی باید دارای موارد زیر باشد:

- عنوان‌های معنادار.
- پاراگراف‌های کوتاه و ساختاریافته.
- جدول‌های قابل پیمایش.
- توضیح اصطلاحات تخصصی.
- تفکیک نتیجه، فرضیه و محدودیت مدل.
- دسترسی به توضیحات تکمیلی بدون وابستگی به Tooltip.

# 10. RTL / LTR ACCESSIBILITY

پشتیبانی از راست‌چین و چپ‌چین باید در سطح ساختار و رفتار پیاده‌سازی شود.

## 10.1. Document Direction

نمونه فارسی:

```html
<html lang="fa" dir="rtl">
```

نمونه انگلیسی:

```html
<html lang="en" dir="ltr">
```

## 10.2. Mixed Direction Content

برای متن‌های ترکیبی باید از روش‌های استاندارد مدیریت جهت استفاده شود.

نمونه:

```html
<bdi dir="ltr">HyDroMA API</bdi>
```

## 10.3. Directional Controls

عناصر جهت‌دار باید با جهت زبان سازگار باشند.

موارد قابل بررسی:

- Breadcrumb.
- Pagination.
- Previous / Next.
- Progress Indicator.
- Navigation Arrows.
- Directional Icons.
- Data Tables.
- Charts.
- Form Alignment.

## 10.4. CSS Logical Properties

در طراحی چندزبانه، استفاده از Logical Properties باید بر وابستگی مستقیم به چپ و راست ترجیح داده شود.

نمونه:

```css
.card {
  margin-inline-start: 1rem;
  padding-inline: 1.25rem;
  border-inline-start: 2px solid var(--border-color);
}
```

## 10.5. RTL Acceptance

تغییر زبان نباید باعث موارد زیر شود:

- جابه‌جایی نامناسب عناصر.
- معکوس شدن داده‌های علمی.
- تغییر نادرست ترتیب اعداد.
- اختلال در نمودارها.
- از بین رفتن Focus.
- تغییر غیرمنتظره رفتار کنترل‌ها.

# 11. FORMS ACCESSIBILITY

# 13. TOUCH TARGET AND MOTOR ACCESSIBILITY

## 13.1. Target Size

بر اساس WCAG 2.2، معیار حداقل اندازه هدف تعاملی در سطح AA باید رعایت شود:

- حداقل 24×24 CSS pixels، مگر در موارد استثناهای تعریف‌شده در استاندارد.

برای تجربه مناسب‌تر در موبایل، هدف طراحی پیشنهادی:

- حداقل 44×44 CSS pixels برای کنترل‌های پرتکرار.

عدد 44×44 یک هدف طراحی داخلی است و نباید با حداقل الزام WCAG اشتباه گرفته شود.

## 13.4. Dragging Alternatives

# 14. MOTION AND ANIMATION ACCESSIBILITY

Motion باید با محدودیت‌های کاربران سازگار باشد.

## 14.1. Reduced Motion

در صورت فعال بودن تنظیم سیستم‌عامل:

```css
@media (prefers-reduced-motion: reduce) {
  *,
  *::before,
  *::after {
    scroll-behavior: auto !important;
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
  }
}
```

این نمونه فقط نقطه شروع است و باید بررسی شود که حذف یا کاهش Motion موجب از دست رفتن اطلاعات یا اختلال عملکرد نشود.

## 14.2. Motion Requirements

- انیمیشن‌های غیرضروری محدود شوند.
- از Flashing خطرناک اجتناب شود.
- اطلاعات ضروری صرفاً با Animation منتقل نشود.
- امکان توقف حرکت‌های طولانی فراهم شود.
- تغییرات سریع و مکرر بصری محدود شوند.
- وضعیت Loading بدون حرکت نیز قابل درک باشد.

## 14.3. Scientific Animation

در شبیه‌سازی‌های HyDroMA:

- امکان Pause وجود داشته باشد.
- امکان توقف و ادامه فراهم باشد.
- زمان شبیه‌سازی مشخص باشد.
- تغییرات مدل قابل توضیح باشند.
- کاربر بتواند به داده‌های عددی دسترسی داشته باشد.
- نتیجه فقط از طریق Animation منتقل نشود.

صفحات باید با بزرگ‌نمایی تا 400 درصد، در شرایط تعریف‌شده WCAG، قابل استفاده باقی بمانند.

## 23.3. Orientation

محتوا نباید بدون ضرورت به یک جهت خاص نمایشگر محدود شود.

## 23.4. Mobile Controls

کنترل‌های موبایل باید:

- اندازه مناسب داشته باشند.
- فاصله مناسب داشته باشند.
- با صفحه‌کلید خارجی قابل استفاده باشند.
- در حالت بزرگ‌نمایی قابل دسترسی باشند.

# 24. ACCESSIBILITY IN LOW-BANDWIDTH ENVIRONMENTS

دسترس‌پذیری فقط به محدودیت‌های جسمی مربوط نیست.

در مناطق روستایی و عشایری، محدودیت اینترنت و سخت‌افزار نیز اهمیت دارد.

## 24.1. Low-Bandwidth Requirements

- محتوای اصلی بدون بارگذاری تصاویر سنگین قابل دسترسی باشد.
- خطاهای شبکه قابل فهم باشند.
- امکان Retry وجود داشته باشد.
- اطلاعات فرم‌ها در خطای موقت از بین نروند.
- وضعیت اتصال مشخص باشد.
- محتوای حیاتی به فایل‌های بزرگ وابسته نباشد.

## 24.2. Progressive Enhancement

عملکرد پایه صفحه باید حتی در شرایط محدود نیز قابل استفاده باقی بماند.

## 24.3. Offline Considerations

در صورت پشتیبانی واقعی محصول از حالت Offline:

- وضعیت آفلاین اعلام شود.
- داده ذخیره‌نشده مشخص باشد.
- زمان آخرین همگام‌سازی نمایش داده شود.
- وضعیت همگام‌سازی قابل فهم باشد.

وجود یک نشانگر Offline به‌تنهایی اثبات عملکرد آفلاین نیست.

# 25. SECURITY AND ACCESSIBILITY

امنیت و دسترس‌پذیری باید هم‌زمان رعایت شوند.

موارد ضروری:

- پیام خطای امنیتی نباید اطلاعات حساس افشا کند.
- احراز هویت چندمرحله‌ای باید قابل استفاده باشد.
- CAPTCHA نباید تنها روش احراز انسان بودن باشد.
- کاربران باید بتوانند خطاهای امنیتی را درک کنند.
- پیام‌های Timeout باید قابل فهم باشند.
- محدودیت دسترسی باید با متن روشن توضیح داده شود.

در عملیات مالی، حذف، انتقال دارایی یا تغییرات حساس، کنترل امنیتی نباید به بهانه سهولت استفاده حذف شود.
