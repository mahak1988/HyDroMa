# 1. Purpose

این سند استانداردهای امنیتی و حریم خصوصی لایه Frontend را برای اکوسیستم Eco Nojin تعریف می‌کند.

هدف، ایجاد رابط کاربری‌ای است که علاوه بر تجربه کاربری مناسب، در برابر تهدیدهای متداول وب مقاوم باشد و از اطلاعات کاربران، داده‌های علمی، اطلاعات مکانی، داده‌های مالی و اطلاعات سازمانی محافظت کند.

امنیت در این سند یک ویژگی مستقل از طراحی بصری نیست؛ بلکه بخشی از معماری تجربه کاربری، مدیریت وضعیت، ارتباط با API و چرخه توسعه Frontend محسوب می‌شود.

این استاندارد باید در سه محصول زیر رعایت شود:

1. Eco Nojin — پلتفرم اصلی و عمومی اکوسیستم.
2. HyDroMA — موتور علمی، محاسباتی، پایش و شبیه‌سازی.
3. Nojin Marketplace — بازارگاه اقتصادی، تجاری و خدماتی.

## 1.1. اهداف اصلی

- کاهش سطح حمله Frontend.
- حفاظت از نشست‌های کاربری و اطلاعات احراز هویت.
- جلوگیری از افشای اطلاعات حساس.
- طراحی امن ارتباط Frontend و Backend.
- جلوگیری از آسیب‌پذیری‌های ناشی از ورودی و خروجی کاربران.
- محافظت از داده‌های مالی و تراکنشی.
- حفاظت از اطلاعات مکانی و داده‌های عملیاتی حساس.
- رعایت اصول Privacy by Design و Privacy by Default.
- کاهش ریسک وابستگی‌های نرم‌افزاری و زنجیره تأمین.
- ایجاد قابلیت ممیزی و ردیابی رخدادهای امنیتی.
- حفظ امنیت در طراحی Responsive، RTL/LTR و تعاملات پیچیده.

## 1.2. اصل بنیادی

وجود کنترل امنیتی در رابط کاربری به‌معنای تأمین امنیت کل سامانه نیست.

Frontend یک محیط اجرایی تحت کنترل کامل کاربر محسوب نمی‌شود. کاربر می‌تواند کدهای سمت مرورگر، درخواست‌های شبکه، وضعیت Local Storage، پارامترهای URL و درخواست‌های API را دست‌کاری کند.

بنابراین:

- Frontend نباید مرجع نهایی مجوز دسترسی باشد.
- Backend باید تمام مجوزها را مستقل از وضعیت رابط کاربری بررسی کند.
- اعتبارسنجی Frontend جایگزین اعتبارسنجی Backend نیست.
- مخفی کردن یک دکمه، کنترل دسترسی محسوب نمی‌شود.
- داده دریافتی از مرورگر نباید بدون اعتبارسنجی قابل اعتماد تلقی شود.

# 2. Security Governance and Reference Frameworks

## 2.1. چارچوب‌های مرجع

طراحی و ارزیابی امنیت باید با توجه به نسخه‌های معتبر و به‌روز چارچوب‌های زیر انجام شود:

| Framework | کاربرد |
|---|---|
| OWASP Top 10 | شناسایی ریسک‌های مهم امنیت برنامه‌های وب |
| OWASP ASVS | تعیین الزامات قابل آزمون امنیت برنامه |
| OWASP WSTG | راهنمای آزمون امنیتی برنامه وب |
| OWASP Cheat Sheet Series | راهنمای کنترل‌های امنیتی تخصصی |
| NIST Cybersecurity Framework | مدیریت ریسک و حاکمیت امنیت |
| NIST Privacy Framework | مدیریت ریسک حریم خصوصی |
| W3C Web Security | الزامات و راهنمای امنیت مرورگر |
| WCAG 2.2 | دسترس‌پذیری تعاملات امنیتی |

این سند از این چارچوب‌ها الهام می‌گیرد، اما ادعای انطباق کامل با هیچ‌یک را مطرح نمی‌کند.

انطباق رسمی تنها پس از ارزیابی مستقل و مستند قابل اعلام است.

## 2.2. سطوح اهمیت

الزامات امنیتی با چهار سطح اولویت مشخص می‌شوند:

| سطح | تعریف |
|---|---|
| CRITICAL | نقصی که می‌تواند به تصاحب حساب، دسترسی غیرمجاز یا افشای گسترده اطلاعات منجر شود |
| HIGH | نقصی با تأثیر جدی بر محرمانگی، یکپارچگی یا دسترس‌پذیری |
| MEDIUM | نقصی با دامنه یا احتمال تأثیر محدودتر |
| LOW | ضعف محدود که باید در چرخه بهبود اصلاح شود |

هیچ آسیب‌پذیری CRITICAL نباید در نسخه Production منتشر شود.

پذیرش ریسک‌های HIGH فقط با تأیید صریح مالک و ثبت مستند ریسک مجاز است.

## 3.2. Trust Boundary

مرز اعتماد باید به‌صورت صریح تعریف شود.

موارد زیر غیرقابل اعتماد هستند:

- ورودی فرم‌ها.
- Query Parameters.

- داده‌های دریافتی از سرویس‌های خارجی.
- اطلاعات موجود در Client State.

هیچ‌یک از این داده‌ها نباید بدون اعتبارسنجی و کنترل مناسب وارد عملیات حساس شوند.

## 3.3. اصل مسئولیت Backend

- Authentication.

- Data Validation.
- Financial Integrity.
- Transaction Integrity.
- Rate Limiting.
- Audit Logging.
- Input Sanitization در محل مناسب.
- کنترل دسترسی به فایل‌ها.
- کنترل دسترسی به داده‌های مکانی و علمی.

Frontend فقط می‌تواند وضعیت مجوزها را برای نمایش مناسب رابط کاربری دریافت کند.

# 4. Authentication and Session Security

## 4.1. اصول احراز هویت

فرایند احراز هویت باید شامل موارد زیر باشد:

- ورود امن.
- خروج امن.
- مدیریت نشست.
- تمدید نشست.
- انقضای نشست.
- بازیابی حساب.
- مدیریت دستگاه‌ها و نشست‌های فعال، در صورت پشتیبانی Backend.
- کنترل تلاش‌های ناموفق.
- جلوگیری از افشای اطلاعات حساب.
- مدیریت تغییر رمز عبور.
- پشتیبانی از MFA در صورت تصویب و پیاده‌سازی.

## 4.2. Token Storage

ذخیره‌سازی Token یکی از مهم‌ترین تصمیم‌های معماری امنیتی است.

### ممنوعیت پیش‌فرض

ذخیره Access Token، Refresh Token یا اطلاعات احراز هویت حساس در Local Storage نباید انتخاب پیش‌فرض معماری باشد.

دلیل اصلی، امکان دسترسی JavaScript مخرب ناشی از XSS به داده‌های ذخیره‌شده در این محیط است.

### گزینه‌های معماری

| روش | ویژگی | ریسک و محدودیت |
|---|---|---|
| HttpOnly Cookie | JavaScript به مقدار Cookie دسترسی ندارد | نیازمند طراحی صحیح CSRF و Cookie Policy |
| Secure Cookie | انتقال فقط روی HTTPS | وابسته به پیکربندی HTTPS |
| SameSite Cookie | کاهش ارسال ناخواسته Cookie در درخواست‌های Cross-Site | جایگزین کامل CSRF Protection نیست |
| In-Memory Token | عدم ماندگاری در Storage | مدیریت Refresh و Reload پیچیده‌تر است |
| Local Storage | دسترسی آسان از JavaScript | ریسک بالاتر در صورت XSS |

انتخاب نهایی باید پس از بررسی معماری واقعی Authentication، دامنه‌های سرویس، API و الگوی نشست انجام شود.

هیچ روش ذخیره‌سازی نباید بدون ارزیابی تهدیدها تصویب شود.

## 4.3. Cookie Security

در صورت استفاده از Cookieهای احراز هویت، ویژگی‌های زیر باید بررسی و در صورت تناسب اعمال شوند:

- HttpOnly
- Secure
- SameSite
- محدودیت Domain
- محدودیت Path
- Expiration
- Session Rotation

برای Cookieهای حساس، استفاده از پیشوند `__Host-` در صورت سازگاری معماری توصیه می‌شود.

Cookie با ویژگی HttpOnly نباید از طریق JavaScript قابل خواندن باشد.

## 4.4. Session Lifecycle

فرایند نشست باید شامل این مراحل باشد:

1. Authentication.
2. Session Establishment.
3. Session Validation.
4. Session Renewal.
5. Session Expiration.
6. Logout.
7. Server-side Session Revocation.

خروج از حساب باید در صورت استفاده از نشست سمت سرور، نشست مربوطه را در Backend نیز باطل کند.

پاک کردن داده‌های رابط کاربری به‌تنهایی Logout امن محسوب نمی‌شود.

## 4.5. Authentication Error Handling

پیام‌های خطا نباید اطلاعات غیرضروری درباره وضعیت حساب افشا کنند.

پیام‌های مناسب:

- اطلاعات ورود معتبر نیست.
- نشست شما منقضی شده است.
- امکان تکمیل درخواست وجود ندارد.
- برای ادامه، مجدداً احراز هویت کنید.

از افشای جزئیات داخلی Authentication، شناسه‌های حساس و اطلاعات فنی Backend خودداری شود.

# 5. Multi-Factor Authentication and Passkeys

## 5.1. MFA

در صورت پیاده‌سازی MFA، رابط کاربری باید از موارد زیر پشتیبانی کند:

- مرحله دوم احراز هویت.
- نمایش وضعیت تأیید.
- مدیریت Timeout.
- امکان بازیابی امن.
- پیام‌های خطای مناسب.
- جلوگیری از ارسال مکرر درخواست.
- نمایش وضعیت نشست پس از تأیید.

## 5.2. Passkeys

در صورت انتخاب Passkeys، پیاده‌سازی باید با استاندارد WebAuthn و FIDO2 سازگار باشد.

Frontend نباید خودسرانه اطلاعات Credential را تولید یا اعتبارسنجی کند.

عملیات ثبت و تأیید Credential باید با همکاری Backend انجام شود.

## 5.3. Account Recovery

بازیابی حساب باید از نظر امنیتی هم‌سطح فرایند ورود طراحی شود.

نباید صرفاً با دسترسی به یک ایمیل یا شماره تماس، امکان تغییر اطلاعات حساس فراهم شود؛ مگر اینکه فرایند اعتبارسنجی مناسب در Backend تعریف شده باشد.

# 6. Authorization and Access Control

## 6.1. Principle of Least Privilege

هر کاربر باید فقط به امکانات و داده‌هایی دسترسی داشته باشد که برای نقش و مسئولیت او ضروری است.

## 6.2. User Roles

نقش‌های احتمالی اکوسیستم:

- Public Visitor
- Registered User
- Village Member
- Rangeland Member
- Producer
- Marketplace Seller
- Marketplace Buyer
- Scientific Analyst
- Field Operator
- Project Manager
- Financial Operator
- Content Editor
- Organization Administrator
- System Administrator

این فهرست پیشنهادی است و به‌معنای تصویب نقش‌ها یا مجوزهای عملیاتی نیست.

## 6.3. Frontend Permission Rendering

Frontend می‌تواند براساس مجوزهای دریافت‌شده:

- منوها را نمایش دهد یا مخفی کند.
- عملیات غیرمجاز را غیرفعال کند.
- پیام دسترسی محدود نمایش دهد.
- مسیر مناسب برای درخواست مجوز ارائه کند.

اما هیچ‌کدام از این رفتارها جایگزین کنترل Backend نیستند.

## 6.4. Object-Level Authorization

برای داده‌هایی مانند:

- اطلاعات یک روستا.
- اطلاعات یک مرتع.
- پرونده یک پروژه.
- گزارش مالی.
- سفارش بازارگاه.
- فایل علمی.
- داده مکانی.
- شبیه‌سازی اختصاصی.

Backend باید مالکیت و مجوز دسترسی به همان شیء را بررسی کند.

مخفی کردن شناسه یا مسیر یک منبع در Frontend، کنترل امنیتی محسوب نمی‌شود.

## 6.5. Tenant Isolation

در صورت پشتیبانی از چند سازمان یا چند قلمرو عملیاتی:

- داده هر Tenant باید از Tenantهای دیگر جدا باشد.
- شناسه Tenant ارسالی از Client قابل اعتماد نیست.
- Backend باید تعلق کاربر به Tenant را بررسی کند.
- تغییر Tenant در رابط کاربری نباید باعث دسترسی به داده‌های دیگر شود.

# 7. Protection Against Web Application Attacks

## 7.1. Cross-Site Scripting (XSS)

XSS می‌تواند باعث اجرای JavaScript مخرب در مرورگر کاربر شود.

### الزامات

- استفاده از خروجی‌های Escape‌شده Framework.
- پرهیز از تزریق HTML خام.
- محدود کردن استفاده از `dangerouslySetInnerHTML`.
- پاک‌سازی محتوای HTML در صورت نیاز واقعی به نمایش HTML کاربر.
- استفاده از کتابخانه Sanitization معتبر و نگهداری‌شده.
- جلوگیری از اجرای Script در محتوای دریافتی از API.
- جلوگیری از قرار دادن داده غیرقابل اعتماد در Contextهای JavaScript، HTML و URL.
- بررسی محتوای Rich Text.
- اعمال Content Security Policy.

### ممنوعیت

استفاده از روش‌های زیر بدون کنترل امنیتی مجاز نیست:

- `eval()`
- `new Function()`
- تزریق مستقیم HTML ناشناس
- اجرای Script دریافتی از API
- ساخت کد JavaScript از ورودی کاربر

هر استثنا باید مستند، محدود و بررسی امنیتی شود.

## 7.2. Content Security Policy (CSP)

CSP باید به‌عنوان یکی از لایه‌های دفاعی در برابر XSS در نظر گرفته شود.

سیاست پیشنهادی اولیه:

- محدودسازی `default-src`.
- محدودسازی `script-src`.
- محدودسازی `style-src`.
- محدودسازی `img-src`.
- محدودسازی `connect-src`.
- محدودسازی `font-src`.
- تعریف `frame-ancestors`.
- استفاده از `object-src 'none'`.
- بررسی `base-uri`.
- استفاده از Nonce یا Hash در صورت نیاز.

### نکات اجرایی

- از استفاده گسترده و بدون ضرورت `unsafe-inline` خودداری شود.
- از `unsafe-eval` اجتناب شود.
- ابتدا CSP در حالت Report-Only ارزیابی شود.
- پس از رفع ناسازگاری‌ها، سیاست اجرایی فعال شود.
- گزارش‌های CSP نباید حاوی اطلاعات حساس باشند.

CSP به‌تنهایی تضمین‌کننده امنیت نیست.

## 7.3. Cross-Site Request Forgery (CSRF)

در معماری مبتنی بر Cookie، ریسک CSRF باید بررسی شود.

کنترل‌های احتمالی:

- SameSite Cookie.
- CSRF Token.
- Origin Validation.
- Referer Validation در شرایط مناسب.
- جلوگیری از عملیات تغییردهنده وضعیت با GET.
- کنترل Backend روی درخواست‌های حساس.

CORS جایگزین CSRF Protection نیست.

## 7.4. Cross-Origin Resource Sharing (CORS)

سیاست CORS باید در Backend یا Gateway تنظیم شود.

الزامات:

- عدم استفاده بی‌دلیل از Wildcard.
- محدودسازی Originهای مجاز.
- محدودسازی HTTP Methods.
- محدودسازی Request Headers.
- بررسی Credentialed Requests.
- عدم انعکاس Origin ناشناس در پاسخ.
- جداسازی محیط توسعه، آزمایش و Production.

CORS کنترل دسترسی به داده یا مجوز اجرای عملیات نیست.

## 7.5. Clickjacking

سیاست‌های مناسب باید از طریق HTTP Security Headers اعمال شوند:

- Content-Security-Policy: frame-ancestors
- X-Frame-Options در صورت نیاز به سازگاری با محیط‌های قدیمی

صفحات حساس مالی و مدیریتی نباید بدون دلیل در Frameهای خارجی قابل نمایش باشند.

## 7.6. Open Redirect

پارامترهای Redirect باید کنترل شوند.

موارد ممنوع:

- Redirect به URL ناشناس.
- اعتماد به URL ارسالی از کاربر.
- پذیرش Schemeهای غیرمجاز.
- استفاده از مقصد Redirect بدون اعتبارسنجی.

در صورت امکان، از مسیرهای داخلی شناخته‌شده به‌جای URL کامل استفاده شود.

## 7.7. DOM-Based Attacks

هر داده‌ای که وارد DOM می‌شود باید از نظر Context بررسی شود.

به‌ویژه:

- Query Parameters.
- Fragment Identifiers.
- URL Parameters.
- داده‌های API.
- متن کاربر.
- محتوای Rich Text.

# 8. Input Validation and Output Handling

## 8.1. Input Validation

اعتبارسنجی Frontend برای تجربه کاربری و کاهش خطا ضروری است.

مواردی که باید بررسی شوند:

- نوع داده.
- طول داده.
- محدوده عددی.
- فرمت تاریخ.
- فرمت مختصات.
- فرمت واحدهای علمی.
- ساختار فایل.
- مقادیر مجاز.
- فیلدهای الزامی.

با این حال، Backend باید اعتبارسنجی مستقل و مرجع نهایی را انجام دهد.

## 8.2. Output Encoding

خروجی باید متناسب با Context مقصد Encode شود.

برای مثال:

- HTML Context.
- JavaScript Context.
- URL Context.
- CSS Context.

یک روش عمومی Sanitization برای همه Contextها کافی نیست.

## 8.3. Rich Text

در صورت پشتیبانی از ویرایشگر متن غنی:

# 12. Secure Build and Deployment

## 12.1. Build Security

فرایند Build باید:

- از Source Code معتبر استفاده کند.
- وابستگی‌های قفل‌شده را نصب کند.

- خطاهای امنیتی بحرانی را متوقف کند.
- Artifactهای محیط‌های مختلف را تفکیک کند.

## 12.2. Production Security Headers

پیکربندی سرور یا Gateway باید Security Headers مناسب را بررسی کند:

| Header | هدف |
|---|---|
| Strict-Transport-Security | الزام استفاده از HTTPS |
| Content-Security-Policy | محدودسازی منابع و Scriptها |
| X-Content-Type-Options | جلوگیری از MIME Sniffing |
| Referrer-Policy | محدودسازی اطلاعات Referrer |
| Permissions-Policy | محدودسازی قابلیت‌های مرورگر |
| X-Frame-Options | دفاع تکمیلی در برابر Clickjacking |

تنظیم دقیق هر Header باید با معماری و سازگاری برنامه تطبیق داده شود.

## 12.3. HTTPS

تمام ارتباطات حساس باید از HTTPS استفاده کنند.

استفاده از HTTP برای Authentication، اطلاعات مالی یا داده‌های حساس مجاز نیست.

Mixed Content باید شناسایی و اصلاح شود.

## 12.4. Source Maps

Source Mapهای Production نباید بدون تصمیم آگاهانه منتشر شوند.

در صورت نیاز به خطایابی، روش نگهداری خصوصی و امن آن‌ها باید مشخص شود.

برچسب علمی یا عمومی بودن یک داده به‌تنهایی سطح مجوز دسترسی را تعیین نمی‌کند.

# 15. Browser Storage and Caching

## 15.1. Local Storage

Local Storage فقط برای داده‌های غیرحساس و غیرمحرمانه، پس از بررسی کاربرد، قابل استفاده است.

موارد زیر نباید در آن ذخیره شوند:

- Access Token حساس.
- Refresh Token.
- اطلاعات بانکی.
- داده‌های هویتی حساس.
- داده‌های محرمانه سازمانی.
- کلیدهای دسترسی.

## 15.2. Session Storage

Session Storage نیز محیطی قابل دست‌کاری و قابل خواندن توسط JavaScript است.

کوتاه‌بودن طول عمر داده، آن را به محیط امن برای نگهداری Secret تبدیل نمی‌کند.

## 15.3. IndexedDB

استفاده از IndexedDB برای داده‌های حجیم یا قابلیت Offline باید با طبقه‌بندی داده و ارزیابی ریسک انجام شود.

داده‌های حساس نباید بدون تصمیم معماری و کنترل مناسب در آن نگهداری شوند.

## 15.4. Cache Policy

برای پاسخ‌های حساس API:

- Cache عمومی نباید فعال باشد.
- سیاست Cache باید در Backend تعیین شود.
- داده‌های خصوصی نباید بین کاربران به اشتراک گذاشته شوند.
- Logout باید وضعیت‌های محلی حساس را پاک کند.
- Cacheهای Service Worker باید بررسی شوند.

استفاده از `Cache-Control: no-store` برای پاسخ‌های حساس، در صورت تناسب با معماری، توصیه می‌شود.

# 27. Implementation Governance

وضعیت هر کنترل باید یکی از موارد زیر باشد:

- TESTED

آزمون موفق بدون بررسی شواهد کافی، وضعیت VALIDATED ندارد.

# 29. Final Principles

اصول غیرقابل چشم‌پوشی این سند:

1. Frontend مرجع نهایی Authorization نیست.
2. هیچ Secret نباید در Bundle عمومی قرار گیرد.
3. Token حساس نباید به‌صورت پیش‌فرض در Local Storage ذخیره شود.
4. تمام عملیات حساس باید در Backend اعتبارسنجی شوند.
5. CORS جایگزین Authorization یا CSRF نیست.
6. اطلاعات مالی نباید براساس وضعیت محلی Client معتبر تلقی شوند.
7. داده‌های مکانی حساس باید سطح دسترسی مشخص داشته باشند.
8. داده‌های کاربران باید به حداقل ضروری محدود شوند.
9. وابستگی‌های نرم‌افزاری باید قابل ردیابی و ممیزی باشند.
10. امنیت باید در طراحی، پیاده‌سازی، آزمون و انتشار بررسی شود.
11. هیچ قابلیت امنیتی بدون شواهد آزمون‌شده، تأییدشده تلقی نمی‌شود.
12. تصمیمات حساس معماری نیازمند تأیید مالک هستند.
