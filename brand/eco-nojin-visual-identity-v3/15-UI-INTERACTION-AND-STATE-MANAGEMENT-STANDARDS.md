# 1. هدف سند

این سند استاندارد رفتار تعاملی رابط کاربری در اکوسیستم Eco Nojin را تعریف می‌کند.

تمرکز اصلی بر این پرسش است:

**وقتی کاربر با یک عنصر رابط کاربری تعامل می‌کند، سیستم دقیقاً چه رفتاری باید داشته باشد؟**

این استاندارد برای جلوگیری از رفتارهای ناسازگار، بازخوردهای مبهم، عملیات تکراری، از دست رفتن داده، نمایش نادرست وضعیت‌ها و ایجاد تجربه کاربری غیرقابل پیش‌بینی تدوین شده است.

اهداف:

1. تعریف رفتار استاندارد برای تعاملات کاربر.
2. ایجاد نظام یکپارچه مدیریت وضعیت UI.
3. تفکیک وضعیت رابط از وضعیت واقعی Backend.
4. استانداردسازی رفتار عملیات هم‌زمان و طولانی.
5. مدیریت خطاها و بازیابی از آن‌ها.
6. جلوگیری از ارسال تکراری عملیات حساس.
7. حفظ وضعیت کاربر هنگام جابه‌جایی بین صفحات.
8. تعریف رفتار مناسب برای محیط‌های علمی، مالی و تجاری.
9. ایجاد قرارداد مشخص میان Frontend، Backend و سرویس‌های داده.
10. فراهم‌کردن امکان آزمون و اعتبارسنجی رفتار رابط.

# 2. اصول بنیادین تعامل

## 2.1. Predictability

کاربر باید بتواند رفتار سیستم را پیش‌بینی کند.

برای هر اقدام باید مشخص باشد:

- چه چیزی قابل کلیک است؟
- چه اتفاقی پس از کلیک رخ می‌دهد؟
- آیا عملیات فوری است یا زمان‌بر؟
- آیا امکان لغو وجود دارد؟
- نتیجه کجا نمایش داده می‌شود؟
- در صورت شکست چه اتفاقی می‌افتد؟

رفتار یکسان باید در صفحات مختلف یکسان باقی بماند، مگر آنکه تفاوت عملکردی مستند وجود داشته باشد.

## 2.2. Immediate Feedback

هر اقدام کاربر باید بازخورد متناسب داشته باشد.

برای مثال:

- کلیک روی دکمه: تغییر وضعیت تعاملی.
- ارسال فرم: نمایش وضعیت پردازش.
- موفقیت عملیات: نمایش نتیجه معتبر.
- شکست عملیات: نمایش خطای قابل فهم.
- انتخاب فیلتر: مشخص‌شدن فیلتر فعال.
- بارگذاری فایل: نمایش پیشرفت و نتیجه.

نباید کاربر در وضعیت نامشخص باقی بماند.

## 2.3. Data Integrity

رابط کاربری نباید وضعیت داده را نادرست نمایش دهد.

برای مثال:

- ارسال درخواست به معنی ذخیره موفق نیست.
- نمایش نتیجه موقت به معنی تأیید نهایی نیست.
- پایان انیمیشن Loading به معنی تکمیل پردازش Backend نیست.
- نمایش عدد در داشبورد به معنی اعتبارسنجی علمی آن نیست.

## 2.4. Reversibility

در صورت امکان، اقدامات باید قابلیت بازگشت داشته باشند.

نمونه‌ها:

- لغو انتخاب
- بازگرداندن فیلتر قبلی
- بازیابی مقدار قبلی فرم
- Undo برای عملیات غیرحساس
- لغو پردازش در صورت پشتیبانی واقعی

عملیات مالی، امنیتی و حذف قطعی باید قواعد تأیید و بازیابی مستقل داشته باشند.

## 2.5. Consistency

تعاملات باید در سه برند از الگوی رفتاری مشترک پیروی کنند؛ با این تفاوت که پیچیدگی و شدت بازخورد متناسب با نوع محصول تنظیم می‌شود.

# 4. مدل استاندارد وضعیت رابط کاربری

## 4.1. وضعیت‌های عمومی

هر قابلیت باید وضعیت‌های مرتبط با عملکرد خود را تعریف کند.

| وضعیت | شناسه پیشنهادی | مفهوم |
|---|---|---|
| Initial | INITIAL | هنوز اقدامی انجام نشده |
| Idle | IDLE | آماده تعامل |
| Loading | LOADING | دریافت یا پردازش |
| Submitting | SUBMITTING | ارسال اطلاعات |
| Success | SUCCESS | عملیات موفق |
| Empty | EMPTY | داده‌ای برای نمایش وجود ندارد |
| Error | ERROR | عملیات ناموفق |
| Warning | WARNING | وضعیت نیازمند توجه |
| Disabled | DISABLED | تعامل مجاز نیست |
| Offline | OFFLINE | ارتباط در دسترس نیست |
| Stale | STALE | داده قدیمی است |
| Partial | PARTIAL | نتیجه ناقص است |
| Pending | PENDING | در انتظار تکمیل |
| Cancelled | CANCELLED | عملیات لغو شده |

این وضعیت‌ها یک واژگان مشترک هستند؛ هر کامپوننت فقط وضعیت‌های مرتبط را پیاده‌سازی می‌کند.

## 4.2. State Machine

برای قابلیت‌های پیچیده، استفاده از مدل ماشین حالت توصیه می‌شود.

نمونه چرخه عمومی عملیات:

```text
INITIAL
   |
   v
IDLE
   |
   v
SUBMITTING
   |
   +-------> ERROR
   |
   +-------> PENDING
                |
                v
             LOADING
                |
        +-------+-------+
        |       |       |
        v       v       v
     SUCCESS  ERROR  CANCELLED
```

این نمودار مفهومی است. چرخه واقعی هر قابلیت باید با قرارداد Backend هماهنگ شود.

## 4.3. ممنوعیت وضعیت‌های متناقض

یک قابلیت نباید هم‌زمان وضعیت‌هایی داشته باشد که از نظر منطقی متناقض‌اند.

برای مثال:

- Success و Error برای یک عملیات واحد.
- Loading و Cancelled برای یک درخواست خاتمه‌یافته.
- Empty و دارای داده معتبر.
- Offline و نمایش نتیجه جدید بدون مشخص‌کردن منبع داده.

در مواردی که چند وضعیت مستقل وجود دارد، باید آن‌ها را در دامنه‌های جداگانه مدل کرد.

# 5. تفکیک UI State از Server State

یکی از الزامات معماری Frontend، تفکیک وضعیت محلی رابط از وضعیت داده‌های سرور است.

## 5.1. UI State

نمونه‌ها:

- باز یا بسته بودن Modal
- تب فعال
- منوی باز
- مقدار موقت فیلتر
- وضعیت نمایش Sidebar
- انتخاب موقت کاربر

## 5.2. Server State

نمونه‌ها:

- اطلاعات کاربر
- فهرست محصولات
- موجودی کالا
- وضعیت سفارش
- اطلاعات مالی
- داده‌های علمی
- نتیجه شبیه‌سازی
- وضعیت پروژه MRV

## 5.3. قواعد

- وضعیت سرور نباید صرفاً از روی وضعیت ظاهری UI حدس زده شود.
- داده دریافتی باید دارای زمان دریافت و در صورت امکان نسخه یا شناسه مرجع باشد.
- داده Cache‌شده باید از داده تازه قابل تشخیص باشد.
- تغییر محلی نباید بدون تأیید معتبر سرور به‌عنوان تغییر نهایی معرفی شود.
- سیاست Cache باید متناسب با حساسیت داده تعیین شود.

# 6. مدیریت تعامل دکمه‌ها

## 6.1. رفتار استاندارد

هر دکمه باید موارد زیر را تعریف کند:

- هدف
- نوع اقدام
- وضعیت فعال
- وضعیت غیرفعال
- وضعیت Loading
- نتیجه موفق
- نتیجه ناموفق
- رفتار صفحه‌کلید

## 6.2. جلوگیری از Double Submission

در عملیات ارسال:

1. با شروع درخواست، وضعیت Submitting فعال شود.
2. ارسال مجدد همان عملیات تا تعیین تکلیف درخواست کنترل شود.
3. در صورت موفقیت، نتیجه از پاسخ معتبر سرور استخراج شود.
4. در صورت خطا، امکان تلاش مجدد مطابق نوع خطا فراهم شود.

برای عملیات حساس، کنترل تکرار درخواست باید در Backend نیز وجود داشته باشد.

## 6.3. Idempotency

برای عملیات حساس و قابل تکرار، در صورت پشتیبانی معماری Backend، از Idempotency Key استفاده شود.

این موضوع به‌ویژه در موارد زیر اهمیت دارد:

- پرداخت
- ثبت سفارش
- انتقال اعتبار
- ثبت تراکنش
- ایجاد پروژه
- اجرای عملیات دارای هزینه

کنترل دکمه در Frontend به‌تنهایی برای تضمین عدم تکرار عملیات کافی نیست.

# 7. مدیریت فرم و ورودی کاربر

## 7.1. چرخه فرم

```text
EMPTY
  |
  v
EDITING
  |
  v
VALIDATING
  |
  +-------> INVALID
  |
  v
SUBMITTING
  |
  +-------> ERROR
  |
  v
SUCCESS
```

## 7.2. حفظ داده فرم

در شرایط زیر، داده معتبر کاربر نباید بدون دلیل از بین برود:

- خطای شبکه
- خطای اعتبارسنجی
- بازگشت از مرحله بعد
- بسته‌شدن تصادفی پنل
- تغییر موقت تب

ذخیره خودکار داده‌ها باید بر اساس حساسیت اطلاعات و سیاست امنیتی محصول انجام شود.

## 7.3. Dirty State

سیستم باید تشخیص دهد که آیا کاربر تغییر ذخیره‌نشده دارد یا خیر.

در صورت تلاش برای خروج:

- هشدار مناسب نمایش داده شود.
- امکان ماندن در صفحه وجود داشته باشد.
- امکان خروج بدون ذخیره، در صورت مجاز بودن، ارائه شود.

## 7.4. Validation Timing

اعتبارسنجی می‌تواند در سه زمان اجرا شود:

- On Change
- On Blur
- On Submit

انتخاب روش باید بر اساس نوع فیلد و تجربه کاربری باشد.

برای داده‌های علمی و مالی، اعتبارسنجی نهایی سمت سرور همچنان الزامی است.

# 8. مدیریت درخواست‌های شبکه

## 8.1. چرخه درخواست

هر درخواست باید وضعیت مشخصی داشته باشد:

- Not Started
- In Progress
- Completed
- Failed
- Aborted
- Timed Out

## 8.2. Timeout

برای درخواست‌های شبکه باید سیاست Timeout مشخص وجود داشته باشد.

در صورت Timeout:

- پیام مناسب نمایش داده شود.
- داده قبلی در صورت معتبر بودن حفظ شود.
- امکان تلاش مجدد ارائه شود.
- وضعیت عملیات نامشخص به‌عنوان موفق ثبت نشود.

## 8.3. Retry Policy

تلاش مجدد باید بر اساس نوع خطا انجام شود.

| نوع خطا | سیاست پیشنهادی |
|---|---|
| Network Failure | تلاش مجدد محدود |
| Timeout | تلاش مجدد کنترل‌شده |
| HTTP 400 | اصلاح درخواست |
| HTTP 401 | مدیریت احراز هویت |
| HTTP 403 | نمایش عدم مجوز |
| HTTP 404 | نمایش عدم وجود منبع |
| HTTP 409 | مدیریت تعارض |
| HTTP 429 | رعایت محدودیت درخواست |
| HTTP 500 | تلاش مجدد محدود در صورت مناسب بودن |

تلاش مجدد خودکار برای عملیات غیرقابل تکرار یا حساس نباید بدون تضمین Idempotency انجام شود.

## 8.4. Race Conditions

در درخواست‌های وابسته به جست‌وجو و فیلتر:

- پاسخ قدیمی نباید نتیجه جدید را بازنویسی کند.
- درخواست‌های غیرضروری در صورت امکان لغو شوند.
- ترتیب پاسخ‌ها نباید به‌عنوان ترتیب صحت داده تلقی شود.
- شناسه یا نسخه درخواست برای کنترل پاسخ استفاده شود.

# 9. مدیریت Loading و پردازش‌های طولانی

## 9.1. انواع بارگذاری

| نوع | کاربرد |
|---|---|
| Initial Loading | بارگذاری اولیه صفحه |
| Inline Loading | بارگذاری بخشی از محتوا |
| Button Loading | پردازش اقدام |
| Skeleton Loading | ساختار محتوای در حال بارگذاری |
| Background Processing | عملیات پس‌زمینه |
| Long-running Job | پردازش طولانی |

## 9.2. عملیات طولانی

برای عملیات علمی و پردازشی:

- شناسه عملیات باید در صورت امکان ثبت شود.
- وضعیت واقعی پردازش از Backend دریافت شود.
- پیشرفت فقط زمانی نمایش داده شود که اطلاعات معتبر وجود داشته باشد.
- زمان تقریبی نباید به‌عنوان زمان قطعی معرفی شود.
- امکان لغو فقط در صورت پشتیبانی واقعی ارائه شود.

## 9.3. Progress Indicator

سه نوع پیشرفت تعریف می‌شود:

**Determinate Progress**

درصد پیشرفت قابل محاسبه و معتبر است.

**Indeterminate Progress**

پیشرفت دقیق قابل محاسبه نیست؛ فقط در جریان بودن عملیات نمایش داده می‌شود.

**Stage-based Progress**

عملیات دارای مراحل مشخص است و تکمیل هر مرحله قابل تأیید است.

نمایش درصد ساختگی برای ایجاد حس پیشرفت ممنوع است.

# 10. مدیریت خطا و بازیابی

## 10.1. طبقه‌بندی خطا

| دسته | نمونه |
|---|---|
| User Input Error | ورودی نامعتبر |
| Validation Error | شکست اعتبارسنجی |
| Authentication Error | احراز هویت ناموفق |
| Authorization Error | عدم مجوز |
| Network Error | قطع ارتباط |
| Server Error | خطای سرور |
| Conflict Error | تعارض داده |
| Domain Error | خطای منطق کسب‌وکار |
| Scientific Error | نامعتبر بودن داده یا مدل |
| Financial Error | شکست عملیات مالی |

## 10.2. ساختار پیام خطا

پیام مناسب باید در صورت نیاز شامل موارد زیر باشد:

- شرح قابل فهم
- علت احتمالی
- اثر خطا
- اقدام پیشنهادی
- امکان تلاش مجدد
- شناسه پیگیری در صورت وجود

## 10.3. Error Boundary

در معماری React، استفاده از Error Boundary برای جلوگیری از فروپاشی کل رابط در اثر خطای یک بخش پیشنهاد می‌شود.

Error Boundary باید:

- خطا را ثبت کند.
- بخش آسیب‌دیده را محدود کند.
- پیام جایگزین ارائه دهد.
- امکان بازیابی کنترل‌شده فراهم کند.

Error Boundary جایگزین مدیریت خطاهای شبکه و Promise نیست.

# 11. مدیریت وضعیت Offline و اتصال مجدد

## 11.1. Offline State

در صورت قطع ارتباط:

- وضعیت اتصال مشخص شود.
- داده Cache‌شده از داده تازه متمایز باشد.
- قابلیت‌های غیرقابل استفاده مشخص شوند.
- عملیات حساس بدون اتصال معتبر اجرا نشوند.
- داده واردشده کاربر تا حد مجاز حفظ شود.

## 11.2. Reconnection

پس از اتصال مجدد:

1. وضعیت ارتباط بررسی شود.
2. درخواست‌های ضروری مجدداً دریافت شوند.
3. داده‌های محلی با داده سرور مقایسه شوند.
4. تعارض‌ها شناسایی شوند.
5. عملیات معوق فقط طبق سیاست مصوب اجرا شوند.

## 11.3. Offline Queue

صف عملیات آفلاین تنها برای عملیات مشخص و مجاز قابل استفاده است.

عملیات مالی، پرداخت و تغییرات حساس نباید بدون طراحی صریح سازگاری و تضمین‌های امنیتی در صف آفلاین قرار گیرند.

# 12. مدیریت State در داشبوردها

داشبوردها ممکن است چندین منبع داده مستقل داشته باشند.

## 12.1. استقلال وضعیت ویجت‌ها

هر ویجت باید وضعیت مستقل داشته باشد.

برای مثال، شکست دریافت اطلاعات آب نباید باعث از کار افتادن نمایش شاخص‌های اقلیمی شود.

## 12.2. Data Freshness

برای هر بخش داده، در صورت اهمیت، موارد زیر نمایش داده شود:

- زمان آخرین به‌روزرسانی
- منبع داده
- وضعیت دریافت
- وضعیت اعتبارسنجی
- قدیمی یا تازه بودن داده

## 12.3. Partial Dashboard

در صورت شکست بخشی از داده‌ها:

- بخش‌های سالم نمایش داده شوند.
- بخش‌های ناموفق وضعیت خطای مستقل داشته باشند.
- کل داشبورد به‌اشتباه خالی معرفی نشود.

# 13. مدیریت تعاملات علمی HyDroMA

## 13.1. انتخاب محدوده مکانی

کاربر باید بتواند در صورت پشتیبانی قابلیت:

- محدوده را انتخاب کند.
- محدوده را تغییر دهد.
- محدوده انتخابی را مشاهده کند.
- سیستم مختصات را بررسی کند.
- محدودیت مکانی را تشخیص دهد.

## 13.2. انتخاب بازه زمانی

- تاریخ شروع و پایان معتبر باشند.
- ترتیب زمانی صحیح باشد.
- منطقه زمانی مشخص باشد.
- محدودیت داده تاریخی اعلام شود.
- داده مشاهده‌شده از داده پیش‌بینی‌شده تفکیک شود.

## 13.3. تغییر پارامتر مدل

در صورت تغییر پارامترها:

- وضعیت سناریو به‌روزرسانی شود.
- مشخص شود که نتیجه قبلی هنوز با ورودی فعلی سازگار نیست.
- اجرای جدید فقط با اقدام مشخص کاربر یا سیاست مصوب آغاز شود.
- پارامترهای استفاده‌شده در اجرای قبلی حفظ شوند.

## 13.4. نمایش نتیجه علمی

نتیجه باید به اجرای مشخص مدل و نسخه مشخص آن متصل باشد.

تغییر ورودی نباید نتیجه قبلی را بدون اطلاع کاربر به‌عنوان نتیجه جدید نمایش دهد.

## 13.5. Uncertainty Interaction

کاربر باید در صورت وجود داده معتبر بتواند:

- دامنه عدم قطعیت را مشاهده کند.
- روش محاسبه آن را بررسی کند.
- محدودیت‌های تفسیر را بخواند.
