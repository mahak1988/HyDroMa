# 1. هدف سند

این سند قواعد تبدیل هویت بصری به تجربه دیجیتال را تعریف می‌کند.

هدف آن پاسخ به این پرسش است:

هویت بصری نهایی Eco Nojin، HyDroMA و Nojin Marketplace چگونه باید در یک محصول دیجیتال واقعی، شامل صفحات عمومی، داشبوردهای علمی، بازارگاه، صفحات اطلاعاتی و رابط‌های تعاملی، نمایش داده شود؟

این سند باید تضمین کند که:

- هویت بصری در تمام صفحات یکپارچه باقی بماند.
- سه برند شخصیت مستقل خود را حفظ کنند.
- تجربه کاربری از کیفیت بصری قربانی نکند.
- صفحات صرفاً مجموعه‌ای از کارت‌ها و پنل‌های تکراری نباشند.
- محتوای علمی و داده‌های پیچیده قابل فهم ارائه شوند.
- صفحات عمومی از صفحات عملیاتی متمایز باشند.
- رابط کاربری در موبایل، تبلت و دسکتاپ کیفیت مناسبی داشته باشد.
- اجرای فرانت‌اند از تصمیمات مصوب طراحی پیروی کند.

**محدودیت مهم:** این سند مجوز پیاده‌سازی یا تغییر هویت بصری نیست. پیاده‌سازی نهایی تنها پس از تأیید مالک و تعیین نسخه مصوب Design System مجاز خواهد بود.

# 2. اصول بنیادین تجربه دیجیتال

## 2.1 Content First

محتوا باید مبنای طراحی باشد.

ابتدا باید مشخص شود کاربر در هر صفحه به چه اطلاعاتی نیاز دارد؛ سپس ساختار بصری متناسب با آن طراحی شود.

استفاده از عناصر تزئینی، کارت‌ها، نمودارها یا انیمیشن‌هایی که ارزش اطلاعاتی یا عملکردی ندارند، مجاز نیست.

## 2.2 Visual Hierarchy

هر صفحه باید سلسله‌مراتب بصری مشخص داشته باشد.

ترتیب اولویت:

1. هدف اصلی صفحه
2. مهم‌ترین پیام یا داده
3. اقدام اصلی کاربر
4. اطلاعات پشتیبان
5. جزئیات تکمیلی

## 2.3 Distinctive Identity

صفحات نباید به قالب‌های عمومی و بی‌هویت داشبوردهای SaaS تبدیل شوند.

هویت بصری باید از طریق موارد زیر قابل تشخیص باشد:

- تایپوگرافی
- ترکیب رنگ
- فضای سفید
- ساختار صفحات
- ترکیب‌بندی
- سبک تصویر
- رفتار تعاملی
- جزئیات گرافیکی کنترل‌شده

## 2.4 Functional Clarity

زیبایی نباید باعث کاهش وضوح عملکرد شود.

هر عنصر تعاملی باید:

- هدف مشخص داشته باشد.
- رفتار قابل پیش‌بینی داشته باشد.
- وضعیت فعال و غیرفعال آن مشخص باشد.
- در موبایل قابل استفاده باشد.
- با صفحه‌کلید قابل دسترسی باشد.

## 2.5 Scientific Integrity

در صفحات HyDroMA، نمایش بصری داده نباید باعث ایجاد برداشت علمی نادرست شود.

داده واقعی، داده تخمینی، خروجی مدل، سناریوی فرضی و داده شبیه‌سازی‌شده باید از یکدیگر قابل تشخیص باشند.

# 16. قواعد پیاده‌سازی فرانت‌اند

این بخش قراردادهای فنی لازم برای اجرای هویت بصری را تعریف می‌کند.

## 16.1 Design Tokens

- مقادیر طراحی باید از توکن‌ها خوانده شوند.
- استفاده گسترده از مقادیر خام در کامپوننت‌ها ممنوع باشد.
- توکن‌ها باید قابلیت Theme Switching داشته باشند.
- نام‌گذاری توکن‌ها باید پایدار و معنایی باشد.

## 16.2 CSS Architecture

- ساختار CSS باید ماژولار باشد.
- از CSS Logical Properties استفاده شود.
- قواعد RTL و LTR باید از هم تفکیک و قابل آزمون باشند.
- استایل‌های سراسری باید محدود و کنترل‌شده باشند.
- وابستگی‌های غیرضروری به ترتیب DOM ایجاد نشود.

## 16.3 Component Architecture

- کامپوننت‌های مشترک در یک لایه قابل استفاده مجدد قرار گیرند.
- کامپوننت‌های اختصاصی برند در لایه مستقل باشند.
- منطق کسب‌وکار با لایه نمایش مخلوط نشود.
- وضعیت‌های Loading، Error، Empty و Success تعریف شوند.

## 16.4 Asset Management

- فایل‌های فونت و تصویر باید مدیریت نسخه داشته باشند.
- فایل‌های تکراری حذف شوند.
- فرمت و حجم فایل‌ها بهینه باشند.
- مجوز استفاده از Asset ثبت شود.

## 16.5 Performance

- تصاویر باید متناسب با نمایشگر بارگذاری شوند.
- بارگذاری تنبل برای محتوای مناسب استفاده شود.
- از انیمیشن‌های پرهزینه اجتناب شود.
- از ایجاد Layout Shift غیرضروری جلوگیری شود.
- کامپوننت‌های سنگین علمی باید در صورت امکان به‌صورت مرحله‌ای بارگذاری شوند.
