# 3. راهبرد زبان‌های اکوسیستم

## 3.1 زبان‌های پایه

دو زبان پایه طراحی:

- فارسی (fa)
- انگلیسی (en)

این دو زبان باید از ابتدا به‌صورت کامل پشتیبانی شوند.

## 3.2 زبان‌های توسعه آینده

معماری باید قابلیت افزودن زبان‌های دیگر را داشته باشد؛ از جمله:

- عربی (ar)
- ترکی آذربایجانی (az)
- ترکی استانبولی (tr)
- روسی (ru)
- فرانسوی (fr)
- اسپانیایی (es)

وجود این زبان‌ها در فهرست به معنی الزام پیاده‌سازی فوری آن‌ها نیست.

## 3.3 استاندارد کد زبان

استفاده از کدهای استاندارد زبان توصیه می‌شود.

نمونه:

```text
fa
en
ar
az
tr
ru
fr
es
```

در صورت نیاز به تفکیک منطقه‌ای می‌توان از ساختارهای زبان ـ منطقه استفاده کرد.

نمونه:

```text
fa-IR
en-US
en-GB
ar-SA
```

انتخاب Locale باید بر اساس نیاز واقعی محصول انجام شود.

زبان و جهت نوشتار دو مفهوم مرتبط اما مستقل هستند.

سیستم نباید فرض کند هر زبان دارای یک جهت ثابت و غیرقابل تغییر در تمام محتوا است.

- RTL: Right-to-Left
- LTR: Left-to-Right

## 4.2 زبان فارسی

جهت پیش‌فرض:

`rtl`

## 4.3 زبان انگلیسی

جهت پیش‌فرض:

`ltr`

## 4.4 زبان عربی

جهت پیش‌فرض:

`rtl`

## 4.5 سایر زبان‌ها

جهت بر اساس ویژگی زبان و Locale تعیین شود.

## 4.6 قانون معماری

جهت رابط باید از تنظیم زبان یا جهت معتبر دریافت شود و نباید در اجزای متعدد به‌صورت پراکنده و دستی تعریف شود.

# 5. معماری تایپوگرافی

تایپوگرافی باید در سه سطح مدیریت شود:

1. Font Family
2. Font Role
3. Typography Token

## 5.1 Font Family

خانواده فونت شامل مجموعه فایل‌ها و وزن‌های متعلق به یک فونت است.

## 5.2 Font Role

هر فونت باید نقش مشخصی داشته باشد.

نقش‌های پیشنهادی:

| نقش | کاربرد |
|---|---|
| Display | تیترهای بسیار بزرگ |
| Heading | تیترها |
| Body | متن اصلی |
| UI | رابط کاربری |
| Data | اعداد و داده‌های علمی |
| Editorial | محتوای طولانی و تحلیلی |
| Mono | کد و داده‌های فنی |

## 5.3 Typography Token

اندازه، وزن، فاصله خطوط و سایر ویژگی‌ها باید از طریق توکن‌های مرکزی مدیریت شوند.

نمونه:

```text
font.family.display
font.family.heading
font.family.body
font.family.ui
font.family.data
font.family.mono

font.size.xs
font.size.sm
font.size.md
font.size.lg
font.size.xl

font.weight.regular
font.weight.medium
font.weight.semibold
font.weight.bold

line.height.tight
line.height.normal
line.height.relaxed
```

این نام‌ها پیشنهادی هستند و هنوز بخشی از Design System مصوب نیستند.

## 6.4 شبنم

# 19. استاندارد CSS برای RTL/LTR

استفاده از ویژگی‌های منطقی CSS توصیه می‌شود.

نمونه:

```css
.card {
  margin-inline-start: 1rem;
  padding-inline: 1.5rem;
  border-inline-start: 2px solid transparent;
  text-align: start;
}
```

استفاده بی‌رویه از ویژگی‌های فیزیکی مانند:

```css
margin-left
margin-right
padding-left
padding-right
```

در کامپوننت‌های چندزبانه باید اجتناب شود.

## 19.1 مزیت

ویژگی‌های منطقی باعث می‌شوند رفتار کامپوننت بر اساس جهت نوشتار تنظیم شود، بدون اینکه برای هر زبان نسخه جداگانه‌ای از CSS ساخته شود.

# 26. مدیریت فونت در وب

## 26.1 بارگذاری

- فقط وزن‌های موردنیاز بارگذاری شوند.
- از فرمت‌های بهینه و پشتیبانی‌شده استفاده شود.
- فایل‌های فونت از نظر مجوز بررسی شوند.
- بارگذاری فونت نباید موجب اختلال جدی در نمایش اولیه شود.

## 26.2 Font Fallback

برای هر خانواده فونت باید زنجیره جایگزین تعریف شود.

## 26.3 Font Subsetting

در صورت امکان می‌توان زیرمجموعه نویسه‌های موردنیاز را تولید کرد؛ مشروط بر اینکه تمام نویسه‌های لازم برای زبان‌ها و محتوای محصول پوشش داده شوند.

## 26.4 کنترل مجوز

برای هر فونت باید ثبت شود:

- نام
- نسخه
- ناشر
- مجوز
- منبع دریافت
- دامنه استفاده مجاز
- محدودیت توزیع
- تاریخ بررسی
