# 1. هدف سند

این سند استاندارد معماری، طراحی، رفتار و پیاده‌سازی کامپوننت‌ها و الگوهای رابط کاربری اکوسیستم Eco Nojin را تعریف می‌کند.

هدف صرفاً تهیه فهرستی از دکمه‌ها، کارت‌ها و فرم‌ها نیست؛ بلکه ایجاد یک نظام منسجم است که بتواند:

1. تجربه بصری و تعاملی سه برند را هماهنگ کند.
2. از تکرار کد و طراحی جلوگیری کند.
3. توسعه صفحات جدید را سریع‌تر و کم‌هزینه‌تر سازد.
4. رفتار کامپوننت‌ها را در زبان‌های فارسی و انگلیسی یکسان و قابل پیش‌بینی نگه دارد.
5. الزامات علمی و دقت نمایش داده‌ها در HyDroMA را حفظ کند.
6. امکان توسعه بازارگاه، خدمات مالی، گردشگری و داشبوردهای تخصصی را فراهم کند.
7. قابلیت نگهداری، آزمون‌پذیری و توسعه‌پذیری سیستم را افزایش دهد.

**محدودیت مهم:** این سند به‌تنهایی مجوز انتخاب نهایی ظاهر کامپوننت‌ها، تثبیت رنگ‌ها، انتخاب فونت، ایجاد دارایی بصری یا شروع پیاده‌سازی نیست.

تمام مشخصات تا زمان تصویب هویت بصری و Design System در وضعیت پیشنهادی باقی می‌مانند.

# 2. اصول معماری کامپوننت‌ها

## 2.1. اصل Single Source of Truth

هر کامپوننت باید یک مرجع مشخص برای موارد زیر داشته باشد:

- نام و شناسه
- مسئولیت
- طراحی بصری
- رفتار تعاملی
- ورودی‌ها و خروجی‌ها
- وضعیت‌های مختلف
- قواعد دسترس‌پذیری
- تست‌های الزامی
- نسخه و تاریخچه تغییرات

نباید چند پیاده‌سازی مستقل از یک کامپوننت با رفتارهای متفاوت در صفحات مختلف ایجاد شود.

## 2.2. اصل Separation of Concerns

هر کامپوننت باید وظیفه مشخصی داشته باشد.

تفکیک الزامی:

| لایه | مسئولیت |
|---|---|
| Design Tokens | رنگ، تایپوگرافی، فاصله و سایر مقادیر طراحی |
| Primitive Components | عناصر پایه رابط |
| Composite Components | ترکیب چند عنصر پایه |
| Feature Components | اجزای اختصاصی قابلیت‌های محصول |
| Page Patterns | الگوهای ترکیب اجزا در سطح صفحه |
| Application Logic | منطق کسب‌وکار و عملیات |
| Data Layer | دریافت، تبدیل و اعتبارسنجی داده |
| Presentation Layer | نمایش داده و تعامل کاربر |

کامپوننت‌های بصری نباید مستقیماً مسئول اجرای عملیات مالی، محاسبات علمی یا منطق دسترسی باشند.

## 2.3. اصل Reusability

قابلیت استفاده مجدد نباید به قیمت پیچیدگی بیش از حد تمام شود.

یک کامپوننت زمانی باید عمومی شود که:

- در چند بخش واقعاً کاربرد داشته باشد.
- مسئولیت مشخصی داشته باشد.
- API قابل فهمی ارائه دهد.
- وابستگی غیرضروری به یک صفحه نداشته باشد.

از ساخت کامپوننت‌های عمومی برای مواردی که رفتار و ساختار متفاوت دارند خودداری شود.

## 2.4. اصل Composition over Configuration

در موارد مناسب، ترکیب اجزا بر ایجاد یک کامپوننت بسیار بزرگ با ده‌ها گزینه ترجیح دارد.

برای مثال، یک کارت پیچیده داشبورد می‌تواند از بخش‌های Header، Content، Footer و Actions تشکیل شود، به‌جای آنکه تمام این بخش‌ها در یک کامپوننت غیرقابل توسعه ادغام شوند.

# 4. قرارداد عمومی کامپوننت‌ها

هر کامپوننت باید قرارداد مشخصی داشته باشد.

## 4.1. مشخصات پایه

حداقل اطلاعات موردنیاز:

```ts
type ComponentMetadata = {
  id: string;
  name: string;
  version: string;
  status:
    | "proposed"
    | "experimental"
    | "implemented"
    | "tested"
    | "validated"
    | "deprecated";
  owner: string;
  accessibilityLevel: string;
};
```

این ساختار صرفاً یک الگوی پیشنهادی است و الزام به استفاده از همین پیاده‌سازی TypeScript ایجاد نمی‌کند.

## 4.2. قرارداد Props

اصول:

- نام‌گذاری Props باید معنادار باشد.
- مقدار پیش‌فرض باید مشخص باشد.
- ورودی‌های نامعتبر باید کنترل شوند.
- Props نباید مسئولیت‌های نامرتبط را ترکیب کنند.
- تغییرات API باید با نسخه‌بندی هماهنگ باشند.
- کامپوننت باید در برابر داده ناقص رفتار مشخص داشته باشد.

نمونه پیشنهادی:

```ts
type ButtonProps = {
  variant?: "primary" | "secondary" | "tertiary" | "danger";
  size?: "sm" | "md" | "lg";
  disabled?: boolean;
  loading?: boolean;
  fullWidth?: boolean;
  children: React.ReactNode;
  onClick?: () => void;
};
```

این مثال قرارداد اولیه است؛ مقادیر نهایی باید پس از تصویب Design System تثبیت شوند.

## 4.3. ممنوعیت APIهای مبهم

از Propsهایی مانند موارد زیر بدون تعریف روشن پرهیز شود:

```ts
type BadExample = {
  type?: string;
  mode?: string;
  custom?: any;
  config?: object;
};
```

در صورت نیاز به تنظیمات پیچیده، ساختار TypeScript باید صریح و قابل اعتبارسنجی باشد.

# 5. استاندارد وضعیت‌های کامپوننت

هر کامپوننت تعاملی باید وضعیت‌های مرتبط با عملکرد خود را تعریف کند.

## 5.1. وضعیت‌های عمومی

| وضعیت | شرح |
|---|---|
| Default | وضعیت عادی |
| Hover | اشاره‌گر روی عنصر |
| Focus | تمرکز صفحه‌کلید |
| Active | در حال تعامل |
| Disabled | غیرفعال |
| Loading | در حال پردازش |
| Success | عملیات موفق |
| Error | خطا |
| Warning | هشدار |
| Empty | بدون داده |
| Selected | انتخاب‌شده |
| ReadOnly | فقط خواندنی |

وجود تمام وضعیت‌ها برای تمام کامپوننت‌ها الزامی نیست؛ وضعیت‌های مرتبط باید مستند شوند.

## 5.2. وضعیت Loading

- از اجرای چندباره عملیات جلوگیری شود.
- وضعیت انتظار برای کاربر قابل تشخیص باشد.
- در عملیات طولانی، پیام مناسب نمایش داده شود.
- در صورت امکان، عملیات قابل لغو باشد.
- تغییر اندازه غیرضروری کامپوننت هنگام بارگذاری اتفاق نیفتد.

## 5.3. وضعیت Error

- خطا باید قابل فهم باشد.
- اطلاعات حساس فنی نباید به کاربر نمایش داده شود.
- امکان تلاش مجدد در صورت پشتیبانی عملیات وجود داشته باشد.
- خطای اعتبارسنجی از خطای شبکه و خطای مجوز تفکیک شود.

## 5.4. وضعیت Empty

وضعیت بدون داده باید از وضعیت خطا متمایز باشد.

برای مثال:

- هنوز داده‌ای ثبت نشده است.
- فیلترها نتیجه‌ای ندارند.
- داده در حال دریافت است.
- کاربر مجوز مشاهده داده را ندارد.

این وضعیت‌ها نباید با یک پیام عمومی یکسان نمایش داده شوند.

# 6. استاندارد کامپوننت‌های فرم

فرم‌ها در ثبت‌نام، مدیریت پروژه، داده‌های علمی، خرید، گردشگری و عملیات مالی استفاده می‌شوند.

## 6.1. ساختار FormField

هر فیلد در صورت نیاز باید شامل موارد زیر باشد:

1. Label
2. Input Control
3. Required Indicator
4. Helper Text
5. Validation Message
6. Character Counter
7. Accessibility Description

## 6.2. اعتبارسنجی

اعتبارسنجی باید در دو سطح انجام شود:

- Client-side: برای تجربه کاربری و بازخورد سریع.
- Server-side: برای اعتبارسنجی نهایی و امنیت.

اعتبارسنجی سمت کاربر جایگزین اعتبارسنجی سمت سرور نیست.

## 6.3. قواعد تجربه فرم

- خطا نزدیک فیلد مربوط نمایش داده شود.
- خطاهای کلی فرم در ابتدای فرم نیز قابل مشاهده باشند.
- مقادیر معتبر کاربر بدون دلیل پاک نشوند.
- هنگام ارسال، وضعیت پردازش مشخص باشد.
- از ارسال تکراری درخواست جلوگیری شود.
- فیلدهای اجباری به‌روشنی مشخص باشند.
- ترتیب حرکت با صفحه‌کلید منطقی باشد.

## 6.4. فرم‌های مالی

فرم‌های مالی باید قواعد اختصاصی داشته باشند:

- نمایش جداگانه مبلغ و واحد پول.
- عدم استفاده از Floating Point برای محاسبات مالی.
- حفظ دقت اعشاری.
- نمایش صحیح جداکننده هزارگان.
- کنترل مبلغ منفی و نامعتبر.
- نمایش خلاصه پیش از تأیید عملیات حساس.
- ثبت نتیجه عملیات از پاسخ معتبر سرور.

مقادیر مالی در لایه داده باید با Decimal یا معادل دقیق آن مدیریت شوند.

## 6.5. فرم‌های علمی

فرم‌های علمی باید در صورت ارتباط شامل موارد زیر باشند:

- واحد اندازه‌گیری
- دامنه مجاز
- روش ورود مقدار
- منبع داده
- زمان مشاهده
- سیستم مختصات
- دقت اندازه‌گیری
- توضیح روش محاسبه

نباید یک عدد بدون واحد و زمینه علمی به‌عنوان ورودی معتبر پذیرفته شود.

# 7. استاندارد جدول‌ها و داده‌های ساختاریافته

DataTable یکی از اجزای مهم در بخش علمی، مدیریتی و مالی است.

## 7.1. قابلیت‌های پایه

- Sorting
- Filtering
- Pagination
- Column Visibility
- Row Selection
- Responsive Behavior
- Empty State
- Loading State
- Error State

## 7.2. قواعد نمایش

- عنوان ستون‌ها روشن باشد.
- واحد اندازه‌گیری در عنوان یا توضیح ستون مشخص شود.
- مقادیر عددی راست‌چین یا چپ‌چین بودن متناسب با نوع داده داشته باشند.
- تاریخ‌ها با تقویم و زبان انتخابی کاربر هماهنگ باشند.
- اطلاعات مهم تنها با رنگ منتقل نشوند.
- جدول‌های بزرگ از Virtualization یا روش مناسب برای کنترل حجم استفاده کنند.

## 7.3. جدول‌های مالی

- مبلغ بدهکار و بستانکار از یکدیگر متمایز باشند.
- واحد پول صریح باشد.
- مانده حساب به‌صورت مستقل نمایش داده شود.
- ترتیب زمانی تراکنش‌ها مشخص باشد.
- وضعیت تراکنش قابل تشخیص باشد.
- اعداد با دقت حسابداری نمایش داده شوند.

## 7.4. جدول‌های علمی

در داده‌های علمی، نمایش ستون‌های زیر در صورت ارتباط ضروری است:

| ویژگی | نمونه |
|---|---|
| Value | مقدار مشاهده‌شده |
| Unit | واحد |
| Method | روش اندازه‌گیری |
| Source | منبع |
| Timestamp | زمان |
| Spatial Reference | مرجع مکانی |
| Quality Flag | پرچم کیفیت |
| Uncertainty | عدم قطعیت |

مقادیر نمونه صرفاً برای توضیح ساختار هستند.

|---|---|

| Tested | آزمون شده |

نسخه‌بندی پیشنهادی بر مبنای Semantic Versioning است:

- Major: تغییر ناسازگار
- Minor: قابلیت جدید سازگار
