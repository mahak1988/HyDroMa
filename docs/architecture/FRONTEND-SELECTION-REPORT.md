**Inputs:** the four extracted copies in `upstream-registry/frontend-foundations/` (paths from

## 0. خلاصه اجرایی (Persian summary)

- **هیچ‌کدام از چهار پروژه آماده استفاده به‌عنوان پایه محصول نیست**: هیچ‌کدام RTL یا i18n واقعی
  ندارد، هیچ‌کدام Auth/داده واقعی و مستقل ندارد، و سه پروژه `next build` سالم تولید نمی‌کنند.
- **پورتال فعلی خود پروژه (`app/`)** از هر چهار گزینه برای نقش پورتال جلوتر است: بدون وابستگی،
  `lang="fa" dir="rtl"`، توکن‌محور، و ۶۹ تست موفق (شامل اعتبارسنجی علمی).
- پیشنهاد: **گزینه C (Design System + Application Shell اختصاصی با اقتباس انتخابی)** — با پایه
  پورتال موجود و الگوگیری از Nellavio (پوسته کنسول) و Velora (صفحات عمومی/انیمیشن).
- خطای Build با آزمون کنترل‌شده بررسی شد: **به نسخه Next، نسخه Node، تعداد Worker یا یک صفحه خاص
  قابل نسبت‌دادن نیست**؛ در dev همه مسیرها سالم‌اند، در build شکست می‌خورند. جزئیات در §4.
- مجوز کد هر چهار MIT است، اما **مجوز تصاویر/فونت‌های همراه در دو پروژه UNVERIFIED** است.

### 3.2 Transferable components (independent of backend)

- **Nellavio:** `components/common/shadcn/*` primitives, `AdvancedTable`, `DataTablePagination`,
  `PageTitle`, `Navbar` parts (search, notifications, theme, user menu), `SidebarProvider`,
  breadcrumbs, charts wrappers. Coupling: Zustand stores + `next-intl` hooks + `useAuth` context.
- **Kiranism:** `components/ui/*` primitives, `data-table` (column pinning, faceted filters, nuqs
  sync), `kbar` command palette, `forms/*`, theme switcher. Coupling: `nuqs`, Clerk hooks in a few
  nav pieces, TanStack Query provider.
- **Velora:** 101 registry components (copy-in, shadcn registry), 31 blocks, motion primitives
  (aurora, marquee, beams, parallax), pricing tables, navbar/footer variants. Coupling: almost none;
  the registry is designed to be copied.
- **Orbyn:** dashboard cards/charts, timeline, empty states, auth cards, theme customizer (the most
  direct evidence for a token-driven theming mechanism). Coupling: local mock data modules.

### 3.3 Change volume required for Nojin

| Project | Changes to reach a Nojin-grade base | Why |
|---|---|---|
| Nellavio | **High** — 324 physical CSS tokens in 106 files → logical; replace `en/pl` catalogs with fa/ar/en; replace better-auth wiring; replace demo RBAC; fix or bypass the build failure | RTL + i18n + identity are all foreign to it |
| Kiranism | **Very high** — remove/replace Clerk (proxy, layouts, org/billing UI), then add i18n + RTL (166 tokens/104 files in a *smaller* surface) | identity is architectural, not a façade |
| Velora | **Medium** — 166 tokens/104 files, one a11y hiding helper, marquee direction, `DirectionProvider`, Persian typography; no app shell to inherit | it is a marketing/component library, so less app coupling |
| Orbyn | **High** — no auth, no i18n, no data layer, build fails; 386 tokens; licence provenance weak | it is a UI catalogue, not a foundation |

### 3.4 Can components be extracted without dragging dependencies?

Yes for **Velora** (registry model, copy-in) and for **primitive UI kits** in the other three
(button/dialog/table primitives are self-contained). No for anything that touches auth, data fetching
or global stores — in Nellavio/Kiranism those are entangled with context providers.

### 4.2 Controlled build-failure experiments (single-variable)

Baseline: isolated copy of **OrbynAdmin** (`experiments/frontend-build-repro/orbynadmin-context`),
`npm ci` from its own lockfile, then one change at a time.

| # | Variant | Result |
|---|---|---|
| 1 | Next **16.2.10**, Node 26.13, default config | **FAIL** — `InvariantError: Expected workStore to be initialized` on `/orders/[id]`, `/customers/[id]`, `/products/[id]`, `/invoices/[id]`, `/support/[id]` |
| 2 | Next **16.3.7** only (same source, same Node) | **FAIL** — identical invariant, same route family |
| 3 | Node **22.20 LTS** (same build) | **FAIL** — identical invariant; failing route set varies |
| 4 | `export const dynamic = "force-dynamic"` on one failing route | **FAIL** — invariant moves to other static routes (`/dashboard/analytics`, `/apps/ai-chat`) |
| 5 | `experimental.cpus = 1` (1 worker) | **FAIL** — invariant on another route (`/apps/ai-chat`) |
| 6 | `output: "export"` | Different, legitimate error: `Page "/customers/[id]/edit" is missing generateStaticParams()` — the invariant is **not** raised on the export path |

**Conclusion (honest, evidence-bounded):**
the failure is **not** attributable to a Next version, a Node version, worker count, or a single
page. It is an interaction between these starters' app graph and Next 16's page-data/static-
generation pipeline on this platform; the export pipeline avoids it, and dev mode is unaffected.
Nellavio's failure variant is slightly different (`Expected workUnitAsyncStorage to have a store`),
which suggests more than one trigger. Deterministic root-cause attribution to framework vs starter
code is **not established** by these experiments, and no upgrade was applied to the originals.

**Engineering consequence for Nojin:** if Next is selected, `next build` must be a day-one CI gate,
the exact version must be pinned, and "static export vs server build" must be decided explicitly.

## 7. Frontend architecture options

| Criterion (weight) | A: one base for everything | B: base + complementary sources | C: own design system + shell, selective adaptation |
|---|---|---|---|
| Dev cost to first product (20) | 3 | 4 | 3 |
| Speed to market (15) | 5 | 4 | 3 |
| UI quality ceiling (10) | 3 | 4 | 5 |
| Maintenance complexity (10) | 4 | 3 | 3 |
| RTL compatibility (10) | 1 | 1 | 5 |
| i18n compatibility (10) | 2 | 2 | 5 |
| Performance control (5) | 3 | 3 | 4 |
| Security/identity independence (5) | 2 | 3 | 5 |
| Backend independence (5) | 3 | 3 | 5 |
| Licence risk (5) | 3 | 3 | 5 |
| Reusable code (5) | 4 | 5 | 4 |
| **Weighted / 100** | **62** | **65** | **80** |

### Why C wins on evidence, not preference

1. **RTL/i18n cannot be inherited**: 0 logical tokens in all four; a mechanical migration of 324 +
   166 tokens was required in the two least-coupled projects, and pagination/menu semantics still
   need code changes (`DirectionProvider`, flex order).
2. **Identity is the hardest dependency**: Kiranism is unusable offline; Nellavio assumes a server it
   does not ship. Neither can be a base without first deciding D-04.
3. **Build reliability**: 3 of 4 cannot produce a production build; adopting one inherits an
   unresolved build defect at the foundation layer.
4. **The portal already exists in-house** (`app/`): zero dependencies, `lang="fa" dir="rtl"`,
   token-driven, 69/69 tests green. Replacing it with a foreign starter would be a regression in
   RTL/i18n maturity.
5. **Component-level borrowing is cheap and safe**: Velora's registry model, Nellavio's table/nav
   patterns, Orbyn's theme customizer mechanism — all can be re-implemented inside
   `packages/ui` without importing their app shells.

### Recommended shape

```
apps/portal            ← evolve the existing app/ prototype (RTL-first, zero-dep)
apps/console           ← new shell: logical-property utilities, fa/ar/en catalogs, Radix DirectionProvider
apps/scientific-workspace ← shares console shell + packages/ui
packages/design-system ← tokens (from brand/), Persian/Latin type scale, motion tokens
packages/ui            ← adapted primitives (table, dialog, dropdown, form, chart wrappers)
packages/i18n          ← fa/ar/en catalogs, number/date/calendar formatting, RTL helpers
```

Borrowed (patterns, not files): Nellavio's `AdvancedTable`/pagination/navbar composition, Velora's
motion/background blocks and pricing sections, Orbyn's CSS-variable theme customizer.

### Fallback if speed dominates (documented, not recommended)

Option B with **Nellavio** as the console base is the only viable "one base" path: it is MIT, has
i18n routing, an RBAC shape, a working dev server and a passable lint/typecheck. Cost: you own a
starter's debt (50 failing tests, demo auth, no RTL) and must fix its build failure first.

## 8. Limitations

- Kiranism's UI behaviour could not be exercised at all (Clerk); its assessment is source-based.
- Orbyn's provenance is weak (single author, 2026-07, no releases); treat as a pattern catalogue.
- The build defect's exact internal trigger remains unidentified; only its boundaries are proven.
- Asset licences for bundled images in Nellavio and Kiranism are unverified.
- No performance or accessibility audit was performed beyond lint/test/console-error checks.
