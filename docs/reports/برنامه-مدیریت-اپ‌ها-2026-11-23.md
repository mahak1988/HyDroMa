# برنامهٔ مدیریت اپ‌ها در `apps/` — نسخهٔ ۱

**تاریخ:** ۲۳ نوامبر ۲۰۲۶ · **دامنه:** ۹ اپ، ۲۳ پکیج، ۱ سرویس، ۱ موتور
**هدف:** با ۹ اپ و چند نشست موازی، «حافظهٔ مشترک» مخزن دیگر خودکار نیست. این برنامه آن را به قاعده تبدیل می‌کند: هر اپ یک خانهٔ مشخص، یک قرارداد اعلام‌شده، و یک دروازهٔ ورود دارد.

---

## ۰. اصول پنج‌گانه

1. **رجیستری تنها منبع حقیقت:** اپ بدون ورودی در `packages/configuration/apps.json` وجود ندارد — نه در سوئیچر، نه در بیلد، نه در CI.
2. **قرارداد صریح داده:** هر اپ در مانیفست خود اعلام می‌کند داده‌اش از کجاست (`api` / `content` / `offline`) و جایگزینی فیکسچر برای قابلیت قفل‌شده ممنوع است.
3. **درروازهٔ ورود یک اپ (DoD):** رجیستری + واحد مرزها + تست دود e2e + spec دسترس‌پذیری + برابری کلیدهای i18n. بدون این پنج، «اپ» نیست، «نمونه» است.
4. **نشست‌های موازی، مالکیت فایل:** هر اپ در رجیستری `owner` دارد؛ دو نشست هم‌زمان یک اپ را دست نمی‌زنند.
5. **انحراف بزرگ ممنوع:** هیچ کار بسته‌ای بدون کامیت تمام نمی‌شود؛ درخت کاری بیش از ۵۰ فایل تغییرنکرده = توقف و تثبیت.

---

## ۱. رجیستری نسل ۲ (قلب برنامه)

`apps.json` از «لیست مسیر» به «شناسنامهٔ اپ» ارتقا می‌یابد:

```jsonc
{
  "id": "console",
  "path": "/console/",
  "devPort": 5175,
  "audience": "organizations",
  "accent": "console",
  "titleKey": "apps.console.title",
  "bodyKey": "apps.console.body",

  // --- نسل ۲ ---
  "status": "live",              // live | beta | sandbox | archived
  "owner": "session-console",    // مالک فعلی (نشست/نقش)
  "dataMode": "api",             // api | content | offline | hybrid
  "requiresSession": true,
  "apiNamespaces": ["/v1/auth", "/v1/organizations", "/v1/users", "/v1/notifications"],
  "healthRoute": "/console/",
  "tests": { "unit": "apps/console/tests/unit", "e2e": "apps/console/tests", "a11y": true },
  "since": "2026-11-18",
  "notes": "همهٔ داده از API واقعی"
}
```

**ابزار جدید: `scripts/app-manifest.mjs`** — پنج‌سویه را می‌سنجد و در `verify` می‌نشیند:
1. هر پوشهٔ `apps/*` ⇄ ورودی رجیستری (دو طرفه).
2. هر ورودی ⇄ workspace ریشه ⇄ `APP_NAMES` در `check-boundaries`.
3. `dataMode=api` ⇒ اپ باید حداقل یک import از `api-client`/`hydroma-client` یا `/api` داشته باشد (کشف ادعای دروغ).
4. `requiresSession=true` ⇒ وجود `RealSessionProvider`/`SessionGate` در درخت اپ.
5. `status=live` ⇒ وجود spec e2e + spec a11y؛ `status=archived` ⇒ مسیر در `archive/`.

خروجی: جدول خطا با کد E-APP-01…05. (پیاده‌سازی: ~۱۲۰ خط، نیم‌روز.)

---

## ۲. چرخهٔ عمر اپ

```
پیشنهاد (ADR) → scaffold → beta → live → archived
```

- **پیشنهاد:** یک ADR کوتاه (قالب ADR-0009) با مخاطب، داده، تصمیم‌های قفل. بدون ADR اپ ساخته نمی‌شود.
- **scaffold:** اسکریپت `scripts/new-app.mjs` در یک فرمان می‌سازد: پوشهٔ vite + router با `routerBasename` + layout روی `app-shell` + `RealSessionProvider` + تست دود e2e + spec a11y + کلیدهای i18n در سه زبان + ثبت رجیستری + ثبت UNITS. (~۱۵۰ خط، ۱ روز) — هدف: اپ دهم بدون کپی‌کاری و بدون فراموشی گیت.
- **beta:** `status: beta` — در سوئیچر با برچسب «آزمایشی»، معاف از a11y کامل با تاریخ انقضا (۳۰ روز).
- **live:** همهٔ گیت‌ها سبز.
- **archived:** انتقال به `archive/legacy-<id>/` + `status: archived` + حذف از سوئیچر و بیلد. (الگوی موجود: `archive/legacy-site`.)

## ۴. قاعدهٔ داده (که اپ «دمو» نشود)

- سه حالت مجاز: `api` (همه‌چیز واقعی)، `content` (محتوای تحریریهٔ ثابت، مثل پورتال/برند)، `offline` (صف محلی با برچسب صریح).
- حالت `hybrid` فقط با تاریخ مهاجرت اعلام‌شده در مانیفست (مثال فعلی: marketplace — کاتالوگ content + فروشندگان api).
- هر جای UI که داده‌اش `content` است و کاربر انتظار «زنده» دارد، برچسب `common.contentData` می‌گیرد (کلید i18n جدید؛ جای `demoData`).
- قابلیت قفل‌شده: بنر «غیرقابل دسترس» + ارجاع به `BLOCKED-CAPABILITIES.md` — بدون جایگزین ساختگی (قانون موجود).
