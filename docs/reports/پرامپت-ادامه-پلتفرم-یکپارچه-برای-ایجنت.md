> این سند یک **پرامپت اجرایی** برای ایجنت ادامه‌دهنده است. آن را کامل بخوان؛ همهٔ دامها و تصمیمهای قبلی اینجا ثبت شده‌اند تا دوباره پول نکنی.

## ۱. مأموریت

پروژه **Eco Nojin / HyDroMA** در `D:\NOJIN` در حال تبدیل از ۹ اپ جدا به **یک پلتفرم یکپارچه روی یک پورت (5180)** است. معماری هدف:

```
پورت 5180 (تک‌مبدأ)
├─ هستهٔ عمومی        /            ← داخل platform SPA (انجام شده — فاز ۱)
├─ گردشگری            /tourism/**  ← فاز ۳ (مهاجرت به SPA)
├─ بازارگاه           /market/**   ← فاز ۴
├─ مدیریت منظر        /landscape/**← فاز ۵ (platform-landscapes + میدانی + admin)

└─ API هم‌مبدأ        /api/**      ← پروکسی به services/api (انجام شده)
```

**قاعدهٔ طلایی:** هیچ دادهٔ ساختگی (demo/mock/fixture) به‌عنوان جایگزین قابلیت واقعی مجاز نیست؛ قابلیت قفل با برچسب «غیرقابل دسترس» نمایش داده میشود (`docs/BLOCKED-CAPABILITIES.md`).

## ۳. قواعد سفت (نقضشان = خرابکاری)

1. **پکیج منیجر فقط pnpm** — و ترتیب آرگومانها حیاتی است: `pnpm --filter @eco-nojin/X run Y` (نه `pnpm run Y --filter X` — با دومی build-all حلقهٔ بیپایان میافتد؛ این باگ را قبلاً اصلاح کردهایم، برنگردان).
2. **کوکی نشست SameSite=Lax است** → هر fetch به API باید **هم‌مبدأ** از مسیر `/api` برود (پروکسی در unified-serve، unified-dev و vite هر اپ وجود دارد). هرگز آدرس مطلق `http://127.0.0.1:8000` در کد فرانت نگذار (در تستهای e2e از Node side اشکال ندارد).
3. **کامیت فقط با درخواست مالک**؛ هر بستهٔ کاری = یک کامیت؛ درخت باز > ۵۰ فایل ممنوع.
4. **دسترسپذیری صفرتحمل**: هر مسیر live باید در spec axe باشد؛ استایل inline فقط با توکنهای واقعی (`--primary`, `--primary-fg`, `--surface`, `--fg`, `--border` — نه `--color-*` که وجود ندارد).
5. **i18n برابری کامل**: اضافهکردن هر کلید به `packages/i18n/src/catalogs/en.ts` یعنی همهٔ ۱۵ فایل زبان (fa/en/ar/de/es/fr/hi*/id/it/ja/ko/pt/ru/tr/zh — *hi و ko فقط re-export از en هستند). تست برابری موجود است.
6. **tsconfig و vitest include ها صریح‌اند**: اپ/پوشهٔ جدید باید به `tsconfig.json` (include) و در صورت لزوم `vitest.config.ts` اضافه شود.
7. **Windows/Powershell دامها**: `git mv` پوشههای apps ممکن است Permission denied بدهد → کپی + `git rm`؛ خروجی `read` پسوردها را redact میکند؛ نوشتن با ابزار write در مسیر D:\ فقط وقتی پوشهٔ والد موجود باشد؛ الگوی کارا: اسکریپت `.mjs` موقت بنویس، اجرا کن، خودش خودش را حذف کند.
8. **بدون سرویس ابری/پولی/credit** در هسته (حافظهٔ پروژه) — لایسنسهای MIT/Apache-2.0/BSD/ISC/OFL آزاد.
9. **بدون عملیات مخرب git**: `reset --hard`، `clean -fd`، `checkout -- .`، force-push ممنوع.

## ۴. دستورالعمل فازها (به ترتیب اجرا)

### فاز ۳ — مهاجرت گردشگری به SPA (بزرگترین اولویت)
**هدف:** `/tourism/**` داخل platform SPA بهصورت lazy section؛ اپ قدیمی tourism آرشیو.
1. کد را جابهجا کن: `apps/tourism/src/{app,pages,components,content,store,styles}` → `apps/platform/src/sections/tourism/…` (ساختار نسبی imports حفظ شود؛ `content` و `store` داخل بخش میمانند).
2. `sections/manifest.ts`: tourism → `internal:true` با `loader: () => import("../sections/tourism/router")`.
3. در روتر platform: routeهای tourism زیر `path:"/tourism"` با `React.lazy` + `Suspense` fallback سبک. توجه: tourism از basename `/tourism/` استفاده میکرده؛ routeهایش relative‌اند — زیر wrapper قرار میگیرند.
4. نکتهٔ نشست: TourismSession (isHost = org kind business) داخل بخش میماند ولی از `useRealSession` ریشه میخواند — provider جدا حذف شود.
5. e2e و a11y گردشگری را به platform tests بیاور و مسیرها را `/tourism/...` کن؛ playwright config پلتفرم فقط یک webServer داری — کافی است.
6. `apps.json`: tourism حذف یا `status:"archived"` + پوشه → `archive/legacy-tourism` (در فاز ۷ نهایی).
7. **پذیرش:** `pnpm run verify` سبز + e2e گردشگری سبز + بودجهٔ باندل (chunk بخشی از 700KB جدا lazy).

### فاز ۴ — بازارگاه (پس از تصمیم مالک دربارهٔ کاتالوگ)
تصمیم: کاتالوگ content بماند یا API سازمان‌محور شود — **قبل از شروع از مالک بپرس**. مهاجرت ۱۲ مسیر مثل فاز ۳. سبد/سفارش: store محلی میماند (پرداخت واقعی نیست — برچسب صریح).

### فاز ۵ — مدیریت منظر (بزرگترین؛ ۵ روز)
1. مسیرهای واقعی platform-landscapes را از content/pages.ts به بخش `/landscape` منتقل کن (صفحات اسنادی تکراری حذف؛ ~۳۰ مسیر واقعی).
2. `field-collection` → `/landscape/field` + همگامسازی واقعی: صف localStorage → `POST /v1/resources/surveys` با `requiresSession:true`؛ وضعیت pending/synced/failed واقعی از پاسخ API.
3. console → `/landscape/admin`: سازمانها/اعضا/دعوتنامهها/کاربران/اعلانها (کد console آماده است؛ کافی است زیر بخش مهاجرت کند)؛ پروفایل/امنیت → هستهٔ عمومی `/profile`, `/security`.
4. console قدیمی آرشیو؛ تستهایش به platform منتقل.

### فاز ۶ — HyDroMA علمی (۳ روز + نیم روز بک‌اند)
1. `GET /v1/runs` به services/api اضافه کن (جدول jobs از موتور در SQLite خود موتور است — حداقل: اجراهای ثبتشده در resources با type="runs" یا bridge به FastAPI لوکال؛ تصمیم: ساده شروع کن — فهرست اجراهای ثبتشده در DB اصلی) + تست در api.test.mjs.
2. مهاجرت ۱۳ مسیر science به `/science` lazy section؛ `hydroma-client` دستنخورده.
3. a11y + e2e بخش علمی.

### فاز ۷ — جمعآوری (۲ روز)
- حذف نهایی اپهای آرشیوشده از `apps.json` و build:all؛ سوئیچر قدیمی (`AppSwitcher`) اگر بلااستفاده شد از main ها حذف.
- unified-serve فقط SPA را سرو کند (بخشهای خارجی دیگر باقی نمانده).
- گیت بودجهٔ باندل در CI (`docs/architecture/BUNDLE-BUDGET.md`).
- **پذیرش نهایی:** یک پورت، یک SPA، چهار بخش lazy، همهٔ گیتها سبز.

### فاز ۸ — سختسازی (۲ روز)
- زبانها: هستهٔ platform از content خودش ۱۵ زبان دارد؛ کلیدهای مشترک (auth/sections/apps) را برای ۱۵ زبان کامل کن (قاعدهٔ ۵).
- اسناد: ADR شمارهٔ بعدی ۰۰۱۰ «پلتفرم یکپارچه»؛ بهروزرسانی ROUTING و apps/README.

## ۵. دستورات روزمرهٔ تو

```bash
cd D:\NOJIN
pnpm run verify                      # گیت کامل (قبل از هر کامیت)
pnpm run check:apps                  # سازگاری رجیستری
pnpm run test:api                    # تستهای سرویس
```
