# برنامهٔ توسعه‌محور: تبدیل ۹ اپ به یک پلتفرم یکپارچه (یک پورت)

**تاریخ:** ۲۰۲۶-۱۱-۲۳ · **مبنای مطالعه:** پیمایش مجدد `apps/` (۹ اپ، ~۱۸۹ فایل src، ~۱۶۰ مسیر) + بررسی `app-shell/modules.ts` (رجیستری ماژول تازه) + وضعیت گیت‌ها (۳۸۰ تست واحد + ۱۲ API، همه سبز)
**جایگاه سند:** مکمل «برنامه مدیریت اپ‌ها» است؛ آن سند حکومت می‌کند (کlio فرمان)، این سند نقشهٔ راه **توسعهٔ محصول** را می‌چیند.

---

## ۰. وضعیت امروز (زمین بازی)

| واقعیت | معنی برای این برنامه |
|---|---|
| یک پورت (۵۱۸۰) و یک مبدأ از قبل هست، اما با **۹ باندل جدا**؛ عبور بین اپها = document navigation (لینک `<a>`) | «یکپارچه» هنوز UX نیست؛ فقط ترابرد است |
| `app-shell` جدیداً `createModuleRegistry` دارد و platform مسیرهایش را به‌عنوان ماژول ثبت کرده | زیرساخت مسیر درست **نصفه ساخته شده**؛ باید کامل شود |
| نشست واقعی (RealSessionProvider) فقط در console/market/tourism هست؛ portal/public بدون نشست | هستهٔ عمومی باید نشست بگیرد (ورود/ثبتنام از سایت عمومی) |
| console کاملاً API واقعی؛ science به موتور پایتونی وصل است (۳۱۷ تست)؛ market/tourism نیمهواقعی | مهاجرت بخش‌ها ارزان‌تر از ساخت از صفر است |
| ۲۰۱ فایل کامیتنشده + دو مدیر بسته | پیش‌نیاز فاز ۰ |

**هدف نهایی (پذیرش مالک):** یک اپ SPA واحد روی پورت ۵۱۸۰ با شِل واحد، یک نشست، یک ناوبری؛ هستهٔ عمومی در ریشه و چهار بخش تخصصی: **گردشگری، بازارگاه، مدیریت منظر، HyDroMA** — هر بخش lazy-load؛ باندل اولیه سبک.

---

## ۱. معماری هدف

```
پورت ۵۱۸۰ (تک‌مبدأ)
├─ هستهٔ عمومی پلتفرم          /            ← home + portal (بدون نشست لازم)
├─ بخش گردشگری                  /tourism/**  ← lazy
├─ بخش بازارگاه                 /market/**   ← lazy
├─ بخش مدیریت منظر              /landscape/** ← lazy  (platform-landscapes + field + admin)
├─ بخش علمی HyDroMA             /science/**  ← lazy
├─ ابزار طراحان (sandbox)       /brand/**    ← lazy، خارج از ناوبری اصلی
└─ API هم‌مبدأ                  /api/**      ← پروکسی به services/api (موجود)
```

- **یک اپ runtime** (`apps/platform`) با router ریشه‌ای react-router 7؛ هر بخش یک ماژول lazy با `createModuleRegistry` (زیرساخت موجود) + گیت مخاطب (`preRegisterCheck`).
- **یک RealSessionProvider در ریشه** — همهٔ بخشها از یک نشست می‌خوانند؛ نقشها از API (owner/admin/manager/member/viewer).
- **باندل اولیه** فقط شِل + هستهٔ عمومی (~باندل فعلی portal)؛ بخشها با `React.lazy` و بودجهٔ باندل (سند موجود BUNDLE-BUDGET).
- **ترابرد:** در طول مهاجرت، بخشِ هنوز نیامده همان باندل قبلی پشت هم‌مبدأ می‌ماند؛ سوئیچر آن را به‌عنوان «ماژول خارجی» نشان میدهد. آخرِ کار باندلهای قدیمی آرشیو میشوند.

### جایگزین رد‌شده (و چرا)
- **Module Federation / import-map:** استقلال بیلد را نگه میدارد ولی پیچیدگی نسخه‌های اشتراکی و session sharing را میآورد و UX «یک پلتفرم» را کامل نمیکند؛ برای تیم کوچک ما هزینه > فایده.
- **وضع موجود (۹ باندل):** کار فنی انجام شده ولی تجربه یکپارچه نمیدهد؛ به‌عنوان پل مهاجرت حفظ میشود.

## ۲. نقشهٔ مسیر هدف (تجمیع ۱۶۰ مسیر فعلی)

| بخش | مسیرها | منبع مهاجرت |
|---|---|---|
| عمومی | `/`, `/ecosystem`, `/hydroma`, `/landscape`, `/market`, `/tourism`, `/mrv`, `/knowledge`, `/about`, `/contact`, `/partner`, `/login`, `/register` | home + portal (۲۵ مسیر) |
| گردشگری | مقصدها، عشایری، اقامت، تجربهها، تورها، رویدادها، نقشه، میزبان، رزروها (۱۷) | tourism |
| بازارگاه | کاتالوگ، دستهها، فروشگاهها، محصول، فروشنده، سبد، پرداخت، سفارشها، فضای فروشنده (۱۲) | marketplace |
| مدیریت منظر | اطلس، روستاها، مراتع، مزارع، ارزیابی، طرح مدیریت، بازآفرینی، پایش، اقتصاد، گزارشها، میدانی (`/field`)، مدیریت (`/admin`: سازمانها/کاربران/اعلانها) | platform-landscapes + field-collection + console |
| HyDroMA | مدلها، اجرا، آب، خاک، اقلیم، پوشش، سنجش‌ازدور، شبیهسازی، سناریوها، پروژهها، نقشه | scientific-workspace |
| sandbox | `/brand/**` | brand (status: sandbox) |

**تصمیم ساختاری داخل بخش منظر:** ابزارهای مدیریت سازمان/کاربر از console به `/landscape/admin` می‌روند (سازمان‌ها برای مدیریت منظر وجود دارند)؛ پروفایل/امنیت به هستهٔ عمومی (`/profile`, `/security`) چون همهٔ بخشها از همان نشست میخوانند.

## ۳. فازهای توسعه (هر فاز یک ارزش قابل تحویل)

### فاز ۰ — تثبیت (پیش‌نیاز؛ نیم روز)
کامیت ۲۰۱ فایل باز + حکم مدیر بسته (npm یا pnpm) + اجرای verify. *بدون این فاز هیچ مهاجرتی شروع نمیشود.*

### فاز ۱ — هستهٔ عمومی پلتفرم (۳ روز)
- `apps/platform` → SPA ریشه‌ای: شِل (هدر + ناوبری + فوتر) روی `app-shell`، `RealSessionProvider` ریشه‌ای.
- مهاجرت صفحههای عمومی portal + home به هسته؛ `/login` و `/register` واقعی (AuthPanel موجود) روی سایت عمومی.
- apps.json: `portal`/`home` → `merged`؛ رجیستری ماژول شامل بخشهای هنوزخارجی با پرچم external.
- **تحویل ارزشمند:** کاربر از سایت عمومی ثبتنام/ورود میکند؛ ناوبری یکپارچه.
- **پذیرش:** e2e دود عمومی + axe عمومی سبز؛ باندل اولیه زیر بودجه.

### فاز ۲ — زیرساخت بخشها (۲ روز)
- مانیفست `sections.ts`: id، basePath، loader (lazy)، audience، navLabel، icon؛ + گیت مخاطب.
- قاعدهٔ fallback: مسیر ناشناخته → صفحهٔ ۴۰۴ هسته؛ بخش external → سوئیچر آن را لینک میدهد.
- توسعهٔ `app-manifest` (از برنامهٔ مدیریت): تشخیص بخشهای مهاجرت‌نشده و مسیرهای تکراری.
- **تحویل:** افزودن هر بخش بعدی = یک ورودی مانیفست + یک فایل loader.

### فاز ۳ — بخش گردشگری (۳ روز)
- مهاجرت ۱۷ مسیر + store رزرو + گیت میزبان (org kind=business) + استعلام واقعی `/v1/resources/inquiries`.
- **تحویل:** گردشگری داخل ناوبری یکپارچه با همان نشست. *اولین اثبات الگوی مهاجرت.*

### فاز ۴ — بخش بازارگاه (۳ روز + یک تصمیم مالک)
- **تصمیم مالک لازم:** کاتالوگ `content` بماند یا API سازمان‌محور شود (سند بلوکه‌ها).
- مهاجرت ۱۲ مسیر + سبد/سفارش؛ فروشنده واقعی از نشست.
- **تحویل:** بازارگاه یکجا؛ اگر تصمیم داده گرفته شود، محصولات واقعی.

### فاز ۵ — بخش مدیریت منظر (۵ روز؛ بزرگترین)
- مهاجرت ماژولهای platform-landscapes (فرم/جدول resources موجود) به `/landscape/**`؛ حذف مسیرهای اسنادی تکراری از ۷۴ به صفحات واقعی (~۳۰).
- `field-collection` → `/landscape/field` + همگامسازی واقعی `/v1/resources/surveys` (نشست + صف آنلاین/آفلاین).
- console → `/landscape/admin` (سازمانها/اعضا/دعوتنامهها/کاربران/اعلانها — همه از قبل واقعی).
- **تحویل:** مدیر منظر همه‌چیز را یکجا دارد؛ console قدیمی آرشیو میشود.

### فاز ۶ — بخش علمی HyDroMA (۳ روز + نیم روز بک‌اند)
- مهاجرت ۱۳ مسیر science + اجرای مدل + منشأ؛ endpoint `GET /v1/runs` (فهرست اجراها) در services/api + تست.
- **تحویل:** اجرای مدل از ناوبری پلتفرم با تاریخچهٔ واقعی.

### فاز ۷ — جمعآوری (۲ روز)
- آرشیو باندلهای قدیمی (`archive/legacy-<id>/`)، حذفشان از build:all و سوئیچر، بازنشانی e2e/a11y به مسیرهای جدید، گیت بودجهٔ باندل در CI.
- **پذیرش نهایی:** یک پورت، یک اپ، چهار بخش lazy، همهٔ گیت‌ها سبز.

### فاز ۸ — سختسازی (۲ روز)
- زبانها ۳→۱۵ زیر گیت برابری کاتالوگ؛ کلیدهای i18n بخشهای ادغامشده؛ بهروزرسانی اسناد معماری و ADR (شمارهٔ بعدی: ۰۰۱۰ «پلتفرم یکپارچه»).

**جمع: ~۲۲ تا ۲۵ نفرروز.** ترتیب عمداً ارزش‌محور است: بعد از هر فاز سیستم قابل استفاده است و میشود بین فازها توقف کرد.

## ۴. قرارداد نشست و دسترسی در پلتفرم یکپارچه

| بخش | مخاطب | نشست | نقش لازم |
|---|---|---|---|
| عمومی | همه | اختیاری | — |
| گردشگری | مهمان | اختیاری (مهمان قابل مرور) | میزبان: عضو سازمان kind=business |
| بازارگاه | خریدار/فروشنده | لازم برای سبد/سفارش | فروشنده: سازمان دارای ثبت seller |
| مدیریت منظر | سازمان‌ها | لازم | member برای دیدن، manager+ برای نوشتن، admin+ برای admin |
| HyDroMA | دانشمند | لازم | member+ (محاسبات روی سازمان) |
| admin منظر | اپراتور | لازم | owner/admin |

همهٔ اینها با RBAC پنج‌ردیفهٔ موجود API پوشش داده میشود؛ چیزی جدید لازم نیست.

## ۵. ریسک‌ها و جلوگیری

| ریسک | احتمال | جلوگیری |
|---|---|---|
| بزرگ شدن باندل اولیه | متوسط | lazy بخشی + بودجهٔ باندل گیت CI + اندازهگیری در پایان هر فاز |
| برخورد مسیرها هنگام ادغام | بالا | اعتبارسنج مانیفست (مسیر تکراری = خطا) + جدول مسیر هدف در فاز ۲ |
| شکستن i18n سه‌زبانه | متوسط | گیت برابری کاتالوگ موجود + مهاجرت هر بخش با کلیدهایش |
| رگرسیون در ۱۶۰ مسیر | بالا | تست دود هر بخش قبل و بعد از مهاجرت؛ host پل، پس بخش نیامده همچنان کار میکند |
| تعارض نشستهای موازی | بالا | فیلد owner در رجیستری + فاز ۰ (تثبیت) |
| وابستگی portal به چیدمان اختصاصی | متوسط | مهاجرت به app-shell در فاز ۱ قبل از هر بخش |

## ۶. چیزی که این برنامه نمی‌کند (صادقانه)

- بازنویسی بک‌اند یا موتور: services/api و engines/hydroma دستنخورده میمانند (فقط یک endpoint اضافه میشود).
- قابلیت‌های قفل (Flow Builder، نیروی کار AI، سه‌بعدی): خارج از این نقشه؛ منتظر مجوز مالک.
- چندزبانه‌سازی کامل در یک فاز: فاز ۸ جدا است تا پلتفرم اول یکزبانه درست شود.
